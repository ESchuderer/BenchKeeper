# benchkeeper

Installs, updates and undoes the BenchKeeper agent setup for Claude Code, Codex, Gemini CLI and GitHub Copilot, globally and per project, from a CLI or a local web UI. What the setup contains: the [setup guide](../docs/setup.md#setup-details).

## Quickstart

<!-- generated:quickstart -->
Node.js 22 and at least one agent, Claude Code or Codex ([full list](../docs/setup.md#prerequisites)). Choose the App to review each change in the browser. Choose the CLI in a terminal-only session or in a script.

### App

```sh
npx benchkeeper@6.25.0
```

Opens the browser on the Dashboard with the doctor findings (the read-only checks of this machine). Select Fix everything, review the changes and press Apply; nothing is written before.

### CLI

```sh
npx benchkeeper@6.25.0 plan
```

Lists each change and writes nothing.

```sh
npx benchkeeper@6.25.0 apply
```

Asks per change. `--yes` applies the default selection without questions.

After either path, restart the agents. `npx benchkeeper@6.25.0 history` lists what changed, `npx benchkeeper@6.25.0 undo <run>` reverses a run.

[Lite level, the plugin alone](../docs/setup.md#levels). [Full setup description](../docs/setup.md#setup-details). [What the app writes and what it never does](../docs/setup.md#what-the-app-writes-and-what-it-never-does).

## Setup

Node.js 22 or newer, and at least one agent. Linux and macOS are tested; Windows runs only a CI smoke test (start, plan, apply with a ledger run) and is untested by the owner.

- From npm: `npx benchkeeper@6.25.0 <command>`. A clone of the branch `stable` runs the latest release (each release moves it); to run a change that is not on npm yet, clone the default branch (`--branch main`).
- From a clone: `git clone --depth 1 --branch stable https://github.com/ESchuderer/BenchKeeper.git && npm ci --prefix BenchKeeper/app --omit=dev`, then `node BenchKeeper/app/bin/benchkeeper.mjs <command>`. The web UI needs a build first: `npm ci --prefix BenchKeeper/app && npm run build --prefix BenchKeeper/app`.

Runtime dependencies, pinned: [jsonc-parser](https://github.com/microsoft/node-jsonc-parser) 3.3.1 (JSON settings with comments), [smol-toml](https://github.com/squirrelchat/smol-toml) 1.9.1 (Codex TOML), [yaml](https://github.com/eemeli/yaml) 2.9.1 (workflow files for `projects audit`). The web UI (React, Mantine) is built into `dist/` and ships in the package.

## Commands

`benchkeeper help` lists every option; `benchkeeper help <command> [verb]` or `benchkeeper <command> [verb] --help` prints only that command's lines. An unknown command prints one line on stderr (exit 2), and an old name from before the noun-first rename names its new command.

## Web UI

`benchkeeper ui` serves on `127.0.0.1` at a free port and opens the browser with a one-time link (`--no-open` prints it). The link works once and for 10 minutes, and only as printed: at `http://127.0.0.1:<port>` with the printed port, not at `localhost` or through a forwarded port with another number. A used, expired or wrong-host link, and a tab left open after the server was started again, show what happened; start the app again (`npx benchkeeper@6.25.0`) and open the new link. The browser gets a file only you can read, which forwards to the link, so the token stays out of process arguments other local users can see. The link's token becomes an HttpOnly, SameSite=Strict session cookie named per port (`bk_session_<port>`) and an API key that the page keeps in its own origin's storage. API requests need both: browsers send the cookie to every server on `127.0.0.1`, the key stays with this page. The sessions board frame, which cannot send a header, loads with a one-time ticket the page asks for with the key. The server rejects other Host headers, foreign or `null` origins, cross-site fetches, changes sent with GET, and API requests without the key in the `x-benchkeeper` header. It stops with Ctrl+C in its terminal or with the Stop button in the header, which the server refuses while an apply or eval runs; scans and setup suggestions still running are cancelled. Recorded agent sessions run from the CLI only. Applies, evals and setup suggestions run on the server: while one runs, the header shows it and opens its progress, also after a reload.

The sidebar groups the views: Overview (Dashboard, History), Projects (Projects), Catalog (Skills, Packs), Analysis (Sessions, Runs, Insights, Evals), Agent configuration (Global setup, Agent settings, Rules, Extensions, Accounts), Machine (Automations, Preferences), and Advanced while Editors is on.

## Configuration

| Name | Default | Effect |
|---|---|---|
| `BENCHKEEPER_HOME` | your home directory | the home the app reads and writes; tests point it at a temporary directory |
| `BENCHKEEPER_DEBUG=1` | unset | a failing command prints its stack, masked, instead of only its message (the `ui` server always writes the stack of a failure to its terminal) |
| `BENCHKEEPER_NO_UPDATE_CHECK=1` | unset | no registry request for a newer version (it runs only in a terminal, not when `CI` is set, and never installs) |
| `BENCHKEEPER_SKILLS_CLI=x.y.z` | unset | runs exactly that skills CLI version, which must be at least 7 days old (the install keeps the 7-day cutoff, so a newer one fails instead of running); unset, the newest release at least 7 days old, never below the app's minimum |

Files below `~/.config/benchkeeper/`: `ledger/` (one JSON file per run), `backup/<run>/` (replaced and removed files), `projects.json`, `accounts.json`, `preferences.json` (the app's own preferences: `editors` turns on the editor view, `dismissed` lists the Agent settings notes you dismissed, the settings you decided to keep, the global changes you left unselected in an apply and the Doctor findings you dismissed; while the file does not parse, BenchKeeper reads it as the defaults and writes nothing to it: a dismiss or the Editors switch fails naming the file, and an apply runs without remembering what you left unselected, with a warning), `packs/`, `skills/` (your own skills, one folder each), `evals/` (own cases, `results.jsonl`, outputs of rule cases), `automations/` (own [automation templates](../docs/automations.md)), `automations.json` (the installed automations), `automations-installed/` (copies of the precheck helpers they call), `board.html`, `pack-scopes.json` (the install scope chosen per pack), `disabled-rules/` (global rule files turned off in the Rules view), `kept-rules.json` (global rule files whose edits you keep), `insights-triage.json` (dismissed and snoozed Insights findings), `insights-narrative.json` (the consent to Insights narrative sessions), `orca/` (the optional Orca worker spec and `orca.yaml` and `.worktreeinclude` samples, written when chosen and Orca is installed). Caches below `~/.cache/benchkeeper/`: `worktrees/`, `sessions.json`, `insights-narrative.json` (the last Insights narrative), `webhook.log` (webhook deliveries).

## Test

In the dev container:

- `npm test`: unit tests against temporary home directories with stubbed agent commands
- `npm run smoke`: start, plan, apply and ledger write
- `npm run build && npm run test:ui`: the web UI against a fixture home, axe in light and dark mode

## Release

The app (this package, tag `app-v<x.y.z>`) and the content (`plugins/benchkeeper/`, tag `setup-v<x.y>`) release as two components with their own versions ([releasing](../docs/releasing.md#components)); `test/package.test.mjs` checks that the content's `minApp` is not above the app version. `npm pack` copies rules, own skills, the library catalog and eval sets into `content/` and builds the UI, so `plan` and `apply` work offline for them. After the owner merges a release pull request that raises the app version, the Release workflow starts the "npm publish" workflow (`npm.yml`) with the new version and checks the registry ([releasing](../docs/releasing.md#steps)); a release of the content alone publishes nothing to npm. A manual run of `npm.yml` (Actions, Run workflow, the version as input) is the fallback. It publishes through npm trusted publishing (no token) with provenance. The trusted publisher in the package's npm settings names this repository and `npm.yml`.
