# benchkeeper

Installs, updates and undoes the BenchKeeper agent setup for Claude Code, Codex, Gemini CLI and GitHub Copilot, globally and per project, from a CLI or a local web UI. What the setup contains: the [setup guide](../docs/setup.md#setup-details).

## Quickstart

<!-- generated:quickstart -->
Node.js 22 and at least one agent, Claude Code or Codex ([full list](../docs/setup.md#prerequisites)). Choose the App to review each change in the browser. Choose the CLI in a terminal-only session or in a script.

### App

```sh
npx benchkeeper@6.22.0
```

Opens the browser on the Dashboard with the doctor findings. Select Fix everything, review the changes and press Apply; nothing is written before.

### CLI

```sh
npx benchkeeper@6.22.0 plan
```

Lists each change and writes nothing.

```sh
npx benchkeeper@6.22.0 apply
```

Asks per change. `--yes` applies the default selection without questions.

After either path, restart the agents. `npx benchkeeper@6.22.0 history` lists what changed, `npx benchkeeper@6.22.0 undo <run>` reverses a run.

[Lite level, the plugin alone](../docs/setup.md#levels). [Full setup description](../docs/setup.md#setup-details).

## Setup

Node.js 22 or newer, and at least one agent. Linux and macOS are tested; Windows runs only a CI smoke test (start, plan, apply with a ledger run) and is untested by the owner.

- From npm: `npx benchkeeper@6.22.0 <command>`. Until the first npm release, run it from a clone.
- From a clone: `git clone --depth 1 --branch setup-v6.22 https://github.com/ESchuderer/BenchKeeper.git && npm ci --prefix BenchKeeper/app --omit=dev`, then `node BenchKeeper/app/bin/benchkeeper.mjs <command>`. The web UI needs a build first: `npm ci --prefix BenchKeeper/app && npm run build --prefix BenchKeeper/app`.

Runtime dependencies, pinned: [jsonc-parser](https://github.com/microsoft/node-jsonc-parser) 3.3.1 (JSON settings with comments), [smol-toml](https://github.com/squirrelchat/smol-toml) 1.9.1 (Codex TOML). The web UI (React, Mantine) is built into `dist/` and ships in the package.

## Commands

`benchkeeper help` lists every option.

| Command | Does |
|---|---|
| `ui [--no-open] [--port N]` | the web UI (default command), see [Web UI](#web-ui) |
| `plan`, `apply [--yes] [--all]` | global setup for the installed agents (`--agents a,b`, `--pack matt-pocock`): each change (file changes as a diff, commands as their command line), then a question per change; `--yes` applies the default selection and `--all` every change including removals, both without questions. Plugins are pinned (BenchKeeper from the branch `stable`, which each release moves, at least at this app's version, Ponytail `PONYTAIL_REF`, Matt Pocock's skills `MATT_POCOCK_REF`); one older than its pin gets update steps, a newer one is kept. Plugin state is read from `~/.claude/plugins/` and `~/.codex/config.toml`, the agent CLIs only when those cannot be read. A plugin whose marketplace was added at another ref than the pin is a step by hand, with the commands: moving the marketplace removes it, which deletes the plugin's data. An installed pack plugin whose pack no registered project uses is offered for removal, not preselected (uninstalling deletes the plugin's data) |
| `apply --level lite\|standard\|full` | the install level; default: the level found, full on a machine without BenchKeeper. lite and standard plan the BenchKeeper plugin alone and nothing else on the machine; undo uninstalls it. standard adds the local block that `project apply` writes per repository. `doctor` names the level it finds |
| `history`, `undo <run> [--step s]`, `restore <name>` | recorded runs, undo of a run or step, restore of a `setup.sh` backup folder. A command is undone with its recorded reverse command (an install with its uninstall); a command without one, such as removing a plugin you had, is reported as manual. Undo puts a file back only while it is as the run (or the recorded session) left it and its backup is intact; otherwise it fails for that change and names the file. Each change is journaled before it starts, so a change cut off by a crash shows in history and can be undone |
| `project plan\|apply [dir]` | project setup: `--agents`, `--env container\|host-agent\|sandbox\|host`, `--sandbox`, `--pack`, `--skill`, `--tier`, `--share` or `--local`, `--framework <id>` and `--agent-file <path>` (frameworks, see `frameworks`; `--framework none` takes them out), `--caller lint-js\|lint-python\|sonar` (writes that [repo-baseline](https://github.com/ESchuderer/repo-baseline) caller workflow as a file in the checkout; one that differs from yours is offered, not preselected; no GitHub setting is ever changed). Answers and each community skill's commit are kept in `.benchkeeper/state.json`; a skill recorded at another commit than the library pin is added again at the pin. Undo of a skills CLI command puts back the skill folders and `skills-lock.json` as they were before it, local edits included. A changed answer cleans up: sandbox off removes `sandbox.enabled` and BenchKeeper's excluded commands, a dropped agent loses the `CLAUDE.md` import, the Gemini CLI context setting and skill folders no chosen agent reads. A warning names hand-written AGENTS.md text on where commands run |
| `record [--project dir] -- <agent> [args]` | runs an agent session in a Git repository and records the files it changed (tracked and untracked, not ignored ones) and its Claude Code or Codex transcript when found, so `undo` restores them |
| `frameworks [list]` | the frameworks project setup offers, each with its role, what the install writes, the evidence line and its evaluation file. A workflow owner (`superpowers`) is a singleton: `project apply` refuses a second one, and choosing it takes BenchKeeper's workflow skill and the issue-tracker specs out of that project's block (the `workflow` skill defers to its `Workflow owner:` line). `superpowers` is a Claude Code plugin enabled for the project only (`claude plugin install --scope project` for a shared setup, `--scope local` for a local one, run in the project; undo uninstalls it at that scope; the plugin files stay in the user's plugin cache). `ecc` is the `ecc` pack, four single skills at a pinned commit through the skills CLI (no plugin, no hooks). `agency-agents` is a pick of agent files (`--agent-file engineering/engineering-frontend-developer.md`), each fetched with `curl` from `raw.githubusercontent.com` at a pinned commit into `.claude/agents/`; the file goes to the backup when the pick is dropped. `matt-pocock` is the existing pack. Ids and paths come from the catalog, never from a project's state file. The doctor reports two workflow owners, and an owner installed for the user or the project that the setup did not record. Codex gets none of these: its plugins have no project scope and its agent files need the project's converter |
| `packs list\|save\|export\|import\|remove` | library packs and own packs; a pack file names library skills only; `remove` refuses an own pack a registered project's setup still names and lists those projects |
| `packs enable\|disable <id>.. [--project dir \| --global] [--yes]` | switches packs without a new setup: a plan on top of the saved answers, with a diff and an undo like any run. `--project` (default: the current folder) changes the project's packs, and disabling removes exactly the skills no other enabled pack and no single pick still needs; `--global` installs or removes the plugin of a pack that has one. The checkout stays as it is until the merge is pulled, and the state file is kept in `projects.json` until Update all has written the local setup again. An unmerged branch from an earlier run gets the new commit on top and may hold only commits Update all made (recorded by id in the ledger); a project whose apply or commit fails keeps its worktree under `.cache/benchkeeper/worktrees/` in the home folder until you remove it |
| `board [--no-open]` | the sessions board: writes `board.html` in the `benchkeeper` config folder (readable only by you) and opens it. One row per Claude Code and Codex session from the transcripts in `.claude/projects/` and `.codex/sessions/` below your home folder (Codex subagent rollouts count toward their parent): project, branch, tier and change type from the `Tier:` lines, the pattern (loop, group, Orca worker or single, see the README; Claude Code transcripts only, Codex rollouts give group), setup labels from the skills installed in the session, the BenchKeeper version of the last global apply before it (from `ledger/`), skills used, the last test command's result, pull request state from `gh pr view` (merged kept, open asked again after 6 hours, closed after a day, a failed lookup after 10 minutes), time, tokens, and the cost Claude Code records (API-equivalent; Codex records none). Parsed files are cached by size, modification time and a parser version in `sessions.json` in the `benchkeeper` cache folder (readable only by you), pull request states in `prs.json`. The cache keeps the summary of a session (project, tier, pattern, setup, tokens, cost, tests, pull requests, times, title, and the run id of an Orca worker; never message text) after the agent deletes its transcript, so history older than `cleanupPeriodDays` comes from this cache and starts when the app first scanned; Settings sets how many days summaries stay (default: for good) and clears the cache. The first scan reads every transcript (34 s for 8.9 GB on the test machine), later ones only changed files. Nothing leaves the machine except the `gh` requests |
| `doctor [dir] [--baseline auto\|oss\|private-advisory] [--baseline-ref ref]` | reports without changing anything (`--baseline` adds, per GitHub repository, the drift of merge methods, rulesets, required checks, Actions allowlist, private vulnerability reporting, Dependabot, code scanning, secret scanning and the repo-baseline caller workflows against a profile; read-only `gh api` GET requests, advisory for private repositories, a note instead of an error without `gh`, a login or the network; the profile is read from repo-baseline at the pinned commit, with a bundled copy as fallback; nothing is changed and no rule is proposed. | `doctor` level line | the install level it finds (lite: the plugin, standard: a project setup too, full: the global rules too) and what the next level adds; below full only the plugin is expected |

| `accounts [list]`, `accounts add [name] [--agent claude\|codex] [--container --mount path] [--label text] [--dir path]`, `accounts use\|remove <name>`, `accounts status [name] [--project dir]`, `accounts track <name> [--off] [--project dir] [--yes]`, `accounts limits [name] [--five-hour N] [--seven-day N] [--warn-five-hour N] [--warn-seven-day N] [--pool name\|none] [--auto-pick on\|off] [--when-none stop\|wait] [--continue-below on\|off] [--reset]`, `accounts login <name> [--token] [--email address] [--no-browser] [--project dir]` | several logins per agent, set up through a guided sign-in. An account is a folder of its own on the host (`CLAUDE_CONFIG_DIR` or `CODEX_HOME`, by default `.local/share/benchkeeper/accounts/<name>` below your home folder, mode 0700, never inside the config folder) or a named volume mounted in the project's dev container (`--container --mount <path>`: the folder in the container where the volume is mounted, one its user can write, below its home folder; there is no default because the owner of a new volume depends on the image). The registry, `accounts.json` in the config folder, holds name, agent, folder or volume, label, default and, for a kept token, its creation date: no credential. `add`, `use` and `remove` are plans with a diff, a run in `history` and an undo (`remove` also deletes a stored token, which undo does not restore, and leaves the account's folder and sign-in alone). `login` starts `claude auth login` (`--email` pre-fills the address) or `codex login --device-auth`, takes the sign-in link from its output and opens it in a private window of Firefox (`--private-window`), Chrome or Chromium (`--incognito`) or Edge (`--inprivate`), so the sign-in page asks which account to use; with no such browser, on a machine without a display, for a link of an unknown host or with `--no-browser` it prints the link (Codex also its one-time code) for you to open. When the browser shows a code, paste it at the prompt and it goes to the agent. `--token`: Claude Code `setup-token` (a subscription's one-year token that makes model requests only), kept in the OS credential store (libsecret through `secret-tool`, macOS Keychain through `security`; other systems and a missing service refuse, there is no file fallback), recorded in `accounts.json` as a date, never shown; Codex: the access token piped on stdin goes to `codex login --with-access-token` in the account's folder and is kept nowhere else. A container account runs the sign-in inside the container (`--project`, default the current folder): `devcontainer up` starts it with every container account's volume as a mount, which applies when a container is created (the command that recreates it is printed when the volume is not mounted), and `devcontainer exec --remote-env CLAUDE_CONFIG_DIR=<mount>` runs the agent; the volume survives a rebuild. `status` runs `claude auth status` or `codex login status` with the account's environment (a container account in the `--project` dir's running container) and reports a login that is gone and a kept token older than 11 months (error once a year old) with the command that fixes it; `doctor` reports the same under check `accounts`. Usage (Claude Code): `track` copies one script into `<account folder>/benchkeeper/` and sets it as the account's `statusLine` and as a `StopFailure` hook (matcher `rate_limit\|authentication_failed\|billing_error`) in the account's `settings.json`, next to the hooks already there; an existing `statusLine` of another kind makes the plan an error. The script keeps `usage.json` (per window `used` and `resetsAt`, the read time) and `failures.jsonl` (time and error type, the last 20), mode 0600, nothing else of the input. A host account's change is a plan with a diff, a run in `history` and an undo; a dev container account's files are written through `devcontainer exec` (`--off` reverses, no run). `status`, `doctor` and the Accounts view read the files (a container's through `devcontainer exec cat`): headroom is 100 minus `used_percentage`; a window whose reset time has passed is unknown, never full; below the minimum a warning, below the notice level (default twice the minimum) an info, and the latest failure of each type within 24 hours (`authentication_failed`, `billing_error` warnings, `rate_limit` info). `limits` sets the minimum headroom and notice level per window (defaults 8 and 3 percent, notice 16 and 6) for all accounts or one, the `pool` of an account, and the launch settings; they live in `accounts.json` (`settings`, and `limits` and `pool` per account) and are changed as plans with undo |
| `run [--account name] [--project dir] [--token] -- claude\|codex [args]` | runs the agent as an account (default: the agent's default account, set by `accounts use`) after the same sign-in check; a login that is gone stops the launch with the fix. The environment is the filtered one of the app (no `GH_TOKEN`, API keys or other credentials from your shell) plus the account's one folder variable on the host; an inherited `CLAUDE_CONFIG_DIR` or `CODEX_HOME` is dropped. `--token` (Claude Code) adds the stored token as `CLAUDE_CODE_OAUTH_TOKEN` for that launch only, on the host through the environment and in a container as one more `--remote-env` (visible in the process list of your user while the command runs; it is never written to `devcontainer.json`, the ledger or a log). With a Claude Code account below its minimum headroom in a window, `run` shows the finding (account, window, what is left, reset time) and asks `Start anyway?` (no answer, or input that ends, is no; `--yes` or `accounts limits --continue-below on` answers yes), then hands the terminal to the agent. Opt-in auto-pick (`accounts limits --auto-pick on`, off by default) acts only at this point: for a launch without `--account` whose default account is below its minimum and has a `pool`, the account of that pool with the most headroom (both windows known and at or above their minimum) runs instead and its name is printed; with none, `--when-none stop` (default) refuses with the earliest reset time and `wait` sleeps until it, then starts under that account. Never inside a running session, never outside the pool. BenchKeeper has no command that starts a worker: a worker started through `run` takes the same path |
| `case add --target skill:<name>\|rule:<name> --expected <text> [--should-not]` | records an agent miss as an eval case; the prompt comes from `--run <session run>`, `--transcript`, `--query` or `--description` |
| `test [dir]` | deterministic checks, no agent session: files match the ledger, expected plugins or skill copies, nothing unexpected installed, project community skills at the library pins. Exit 1 on a failure |
| `eval [--agents a,b] [--model m] [--target t] [--all]` | trigger cases (`plugins/benchkeeper/evals/` and your own) as real agent sessions in scratch repositories; miss and false-trigger rates per skill, agent, agent version and model. Uses your subscription, asks first, refuses when `CI` is set; runs only targets whose skill or cases changed unless `--all` |

## Machine-readable output

`doctor`, `test`, `plan`, `project plan`, `history`, `projects list`, `projects scan`, `packs list`, `skills list`, `rules list`, `extensions list`, `settings list`, `settings get`, `frameworks list`, `board`, `profile export`, `maintain knowledge show`, `accounts list` and `accounts status` take `--json`: one JSON document on stdout, logs and error messages on stderr. Every document is an envelope: `schemaVersion` (1), `command` and the keys below, no prose; a failure has `error` instead of the other keys. Values of environment variables and file contents never appear (`maintain knowledge show` prints the entries the maintenance skill stored, with token shapes masked, and no file contents): a change lists its title and path, not its diff, a settings document lists the names of an `env` block without values, and a file that does not parse is reported as such without the parser message. `skills` and `frameworks` also work without the word `list`; any other command or subcommand (`skills update`, `settings set`, `profile import`) is refused with exit 2.

## Web UI

`benchkeeper ui` serves on `127.0.0.1` at a free port and opens the browser with a one-time link (`--no-open` prints it). The browser gets a file only you can read, which forwards to the link, so the token stays out of process arguments other local users can see. The link's token becomes an HttpOnly, SameSite=Strict session cookie named per port (`bk_session_<port>`) and an API key that the page keeps in its own origin's storage. API requests need both: browsers send the cookie to every server on `127.0.0.1`, the key stays with this page. The sessions board frame, which cannot send a header, loads with a one-time ticket the page asks for with the key. The server rejects other Host headers, foreign or `null` origins, cross-site fetches, changes sent with GET, and API requests without the key in the `x-benchkeeper` header. It stops with Ctrl+C in its terminal or with the Stop button in the header, which the server refuses while an apply or eval runs; scans and setup suggestions still running are cancelled. Recorded agent sessions run from the CLI only. Applies, evals and setup suggestions run on the server: while one runs, the header shows it and opens its progress, also after a reload.

## Configuration

| Name | Default | Effect |
|---|---|---|
| `BENCHKEEPER_HOME` | your home directory | the home the app reads and writes; tests point it at a temporary directory |
| `BENCHKEEPER_NO_UPDATE_CHECK=1` | unset | no registry request for a newer version (it runs only in a terminal, not when `CI` is set, and never installs) |

Files below `~/.config/benchkeeper/`: `ledger/` (one JSON file per run), `backup/<run>/` (replaced and removed files), `projects.json`, `accounts.json`, `packs/`, `evals/` (own cases, `results.jsonl`, outputs of rule cases), `board.html`, `orca/` (the optional Orca worker spec and `orca.yaml` and `.worktreeinclude` samples, written when chosen and Orca is installed). Caches below `~/.cache/benchkeeper/`: `worktrees/`, `sessions.json`, `prs.json`.

## Test

In the dev container (repository `AGENTS.md`):

- `npm test`: unit tests against temporary home directories with stubbed agent commands
- `npm run smoke`: start, plan, apply and ledger write
- `npm run build && npm run test:ui`: the web UI against a fixture home, axe in light and dark mode

## Release

The package version equals the plugin version (`plugins/benchkeeper/*/plugin.json`), checked by `test/package.test.mjs`. `npm pack` copies rules, own skills, the library catalog and eval sets into `content/` and builds the UI, so `plan` and `apply` work offline for them. The owner publishes with the "npm publish" workflow (Actions, Run workflow, the version as input), which publishes through npm trusted publishing (no token) with provenance. The trusted publisher in the package's npm settings names this repository and `npm.yml`.
