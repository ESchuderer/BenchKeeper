# benchkeeper

Installs, updates and undoes the BenchKeeper agent setup for Claude Code, Codex, Gemini CLI and GitHub Copilot, globally and per project, from a CLI or a local web UI. What the setup contains: the [repository README](../README.md#setup-details).

## Quickstart

<!-- generated:quickstart -->
Node.js 22 and at least one agent, Claude Code or Codex ([full list](../README.md#prerequisites)). Choose the App to review each change in the browser. Choose the CLI in a terminal-only session or in a script.

### App

```sh
npx benchkeeper@6.11.0
```

Opens the browser on the Dashboard with the doctor findings. Select Fix everything, review the changes and press Apply; nothing is written before.

### CLI

```sh
npx benchkeeper@6.11.0 plan
```

Lists each change and writes nothing.

```sh
npx benchkeeper@6.11.0 apply
```

Asks per change. `--yes` applies the default selection without questions.

After either path, restart the agents. `npx benchkeeper@6.11.0 history` lists what changed, `npx benchkeeper@6.11.0 undo <run>` reverses a run.

[Lite level, the plugin alone](../README.md#levels). [Full setup description](../README.md#setup-details).

## Setup

Node.js 22 or newer, and at least one agent. Linux and macOS are tested; Windows runs only a CI smoke test (start, plan, apply with a ledger run) and is untested by the owner.

- From npm: `npx benchkeeper@6.11.0 <command>`. Until the first npm release, run it from a clone.
- From a clone: `git clone --depth 1 --branch setup-v6.11 https://github.com/ESchuderer/BenchKeeper.git && npm ci --prefix BenchKeeper/app --omit=dev`, then `node BenchKeeper/app/bin/benchkeeper.mjs <command>`. The web UI needs a build first: `npm ci --prefix BenchKeeper/app && npm run build --prefix BenchKeeper/app`.

Runtime dependencies, pinned: [jsonc-parser](https://github.com/microsoft/node-jsonc-parser) 3.3.1 (JSON settings with comments), [smol-toml](https://github.com/squirrelchat/smol-toml) 1.9.1 (Codex TOML). The web UI (React, Mantine) is built into `dist/` and ships in the package.

## Commands

`benchkeeper help` lists every option.

| Command | Does |
|---|---|
| `ui [--no-open] [--port N]` | the web UI (default command), see [Web UI](#web-ui) |
| `plan`, `apply [--yes] [--all]` | global setup for the installed agents (`--agents a,b`, `--pack matt-pocock`): each change (file changes as a diff, commands as their command line), then a question per change; `--yes` applies the default selection and `--all` every change including removals, both without questions. Plugins are pinned (BenchKeeper from the branch `stable`, which each release moves, at least at this app's version, Ponytail `PONYTAIL_REF`, Matt Pocock's skills `MATT_POCOCK_REF`); one older than its pin gets update steps, a newer one is kept. Plugin state is read from `~/.claude/plugins/` and `~/.codex/config.toml`, the agent CLIs only when those cannot be read. A plugin whose marketplace was added at another ref than the pin is a step by hand, with the commands: moving the marketplace removes it, which deletes the plugin's data. An installed pack plugin whose pack no registered project uses is offered for removal, not preselected (uninstalling deletes the plugin's data) |
| `apply --level lite\|standard\|full` | the install level; default: the level found, full on a machine without BenchKeeper. lite and standard plan the BenchKeeper plugin alone and nothing else on the machine; undo uninstalls it. standard adds the local block that `project apply` writes per repository. `doctor` names the level it finds |
| `history`, `undo <run> [--step s]`, `restore <name>` | recorded runs, undo of a run or step, restore of a `setup.sh` backup folder. A command is undone with its recorded reverse command (an install with its uninstall); a command without one, such as removing a plugin you had, is reported as manual. Undo puts a file back only while it is as the run (or the recorded session) left it and its backup is intact; otherwise it fails for that change and names the file. Each change is journaled before it starts, so a change cut off by a crash shows in history and can be undone |
| `project plan\|apply [dir]` | project setup: `--agents`, `--env container\|host-agent\|sandbox\|host`, `--sandbox`, `--pack`, `--skill`, `--tier`, `--share` or `--local`, `--framework <id>` and `--agent-file <path>` (frameworks, see `frameworks`; `--framework none` takes them out), `--caller promote\|lint-js\|lint-python\|sonar` (writes that [repo-baseline](https://github.com/ESchuderer/repo-baseline) caller workflow, pinned to a commit, as a file in the checkout; one that differs from yours is offered, not preselected; no GitHub setting is ever changed). Local (the default): the block goes into `CLAUDE.local.md` and `AGENTS.override.md` (rebuilt from `AGENTS.md` on each apply), the sandbox into `.claude/settings.local.json`, and every file written is listed in a marked block of `.git/info/exclude` (the repository's, shared by its worktrees); `--share` writes the block into `AGENTS.md` with a `CLAUDE.md` import and takes the exclude block out. `--disable <skill>` moves a skill to `.benchkeeper/disabled/`, `--enable` moves it back. Answers and each community skill's commit are kept in `.benchkeeper/state.json`; a skill recorded at another commit than the library pin is added again at the pin. Undo of a skills CLI command puts back the skill folders and `skills-lock.json` as they were before it, local edits included. A changed answer cleans up: sandbox off removes `sandbox.enabled` and BenchKeeper's excluded commands, a dropped agent loses the `CLAUDE.md` import, the Gemini CLI context setting and skill folders no chosen agent reads. A warning names hand-written AGENTS.md text on where commands run |
| `record [--project dir] -- <agent> [args]` | runs an agent session in a Git repository and records the files it changed (tracked and untracked, not ignored ones) and its Claude Code or Codex transcript when found, so `undo` restores them |
| `frameworks [list]` | the frameworks project setup offers, each with its role, what the install writes, the evidence line and its evaluation file. A workflow owner (`superpowers`) is a singleton: `project apply` refuses a second one, and choosing it takes BenchKeeper's workflow skill and the issue-tracker specs out of that project's block (the `workflow` skill defers to its `Workflow owner:` line). `superpowers` is a Claude Code plugin enabled for the project only (`claude plugin install --scope project` for a shared setup, `--scope local` for a local one, run in the project; undo uninstalls it at that scope; the plugin files stay in the user's plugin cache). `ecc` is the `ecc` pack, four single skills at a pinned commit through the skills CLI (no plugin, no hooks). `agency-agents` is a pick of agent files (`--agent-file engineering/engineering-frontend-developer.md`), each fetched with `curl` from `raw.githubusercontent.com` at a pinned commit into `.claude/agents/`; the file goes to the backup when the pick is dropped. `matt-pocock` is the existing pack. Ids and paths come from the catalog, never from a project's state file. The doctor reports two workflow owners, and an owner installed for the user or the project that the setup did not record. Codex gets none of these: its plugins have no project scope and its agent files need the project's converter |
| `packs list\|save\|export\|import\|remove` | library packs and own packs; a pack file names library skills only; `remove` refuses an own pack a registered project's setup still names and lists those projects |
| `packs enable\|disable <id>.. [--project dir \| --global] [--yes]` | switches packs without a new setup: a plan on top of the saved answers, with a diff and an undo like any run. `--project` (default: the current folder) changes the project's packs, and disabling removes exactly the skills no other enabled pack and no single pick still needs; `--global` installs or removes the plugin of a pack that has one. Enabling and then disabling the same pack returns the project's files to what they were |
| `skills [list]`, `skills update\|reset\|remove\|adopt [name..] [--project dir] [--yes]` | skills of one project: `list` gives each skill's state (`current`, `outdated`, `modified`, `removed`, `disabled`), the commit installed and the commit the library offers, and the skill folders no BenchKeeper setup installed (`untracked`, also in the agents' global folders; no update or apply touches them). `update` brings outdated and removed skills to the library's copy (no name: every outdated one); `reset` replaces a skill edited here (the plan shows the diff and the edit goes to the run's backup; a plan without `reset` leaves an edited skill alone); `remove` takes a single pick out of the project (a skill a pack brings leaves with the pack); `adopt` makes an untracked library skill a single pick of the project and keeps its folder. Own skills are compared with the library's files, community skills by the commit and by the hash of their folder recorded when the install ran |
| `projects list\|add\|scan\|remove\|rename\|relocate\|unshare`, `update-all [--yes] [--no-push] [--dry-run] [--max N]` | registered projects (`add` refuses another worktree of a registered repository unless `--worktree`; `rename <dir> [name] [--notes text]` sets the display name and notes in `projects.json`; `relocate <old> <new>` moves the entry, its kept answers and its history to a moved folder; `remove` only unregisters, `remove <dir>.. --setup [--yes] [--no-push]` lists every file, then takes BenchKeeper's setup out and keeps the project registered: a local setup as one run in the checkout (`benchkeeper undo <run>`), a shared one as a pull request on branch `chore/remove-agent-setup`); Update all applies a local setup in the checkout, and for a shared one builds branch `chore/agent-setup-<version>` per project in a worktree, commits, and pushes with a pull request when `origin` is on GitHub. A repository that still tracks `.benchkeeper/state.json` while the setup is local gets a pull request that removes the committed setup (`committedSetup`: the `AGENTS.md` block, an import-only `CLAUDE.md`, BenchKeeper's sandbox keys, the recorded and locked skills, `skills-lock.json`, `.benchkeeper/`) on branch `chore/agent-setup-local`; `projects unshare` does the same for the projects named or all. The checkout stays as it is until the merge is pulled, and the state file is kept in `projects.json` until Update all has written the local setup again. An unmerged branch from an earlier run gets the new commit on top and may hold only commits Update all made (recorded by id in the ledger); a project whose apply or commit fails keeps its worktree under `.cache/benchkeeper/worktrees/` in the home folder until you remove it |
| `board [--no-open]` | the sessions board: writes `board.html` in the `benchkeeper` config folder (readable only by you) and opens it. One row per Claude Code and Codex session from the transcripts in `.claude/projects/` and `.codex/sessions/` below your home folder (Codex subagent rollouts count toward their parent): project, branch, tier and change type from the `Tier:` lines, setup labels from the skills installed in the session, the BenchKeeper version of the last global apply before it (from `ledger/`), skills used, the last test command's result, pull request state from `gh pr view` (merged kept, open asked again after 6 hours, closed after a day, a failed lookup after 10 minutes), time, tokens, and the cost Claude Code records (API-equivalent; Codex records none). Parsed files are cached by size and modification time in `sessions.json` in the `benchkeeper` cache folder (readable only by you), pull request states in `prs.json`. The cache keeps the summary of a session (project, tier, setup, tokens, cost, tests, pull requests, times, title; never message text) after the agent deletes its transcript, so history older than `cleanupPeriodDays` comes from this cache and starts when the app first scanned; Settings sets how many days summaries stay (default: for good) and clears the cache. The first scan reads every transcript (34 s for 8.9 GB on the test machine), later ones only changed files. Nothing leaves the machine except the `gh` requests |
| `doctor [dir] [--baseline auto\|oss\|private-advisory] [--baseline-ref ref]` | reports without changing anything (`--baseline` adds, per GitHub repository, the drift of merge methods, rulesets, required checks, Actions allowlist, private vulnerability reporting, Dependabot, code scanning, secret scanning and the repo-baseline caller workflows against a profile; read-only `gh api` GET requests, advisory for private repositories, a note instead of an error without `gh`, a login or the network; the profile is read from repo-baseline at the pinned commit, with a bundled copy as fallback; applying a profile is repo-baseline's `scripts/apply.mjs`, with a dry run, a snapshot and a restore; `update-all --baseline <profile>` prints the same report per registered project and changes no setting): variables that turn agent features off (`DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_GROWTHBOOK`, `CLAUDE_CODE_DISABLE_ADVISOR_TOOL`; name and file, never the value), rules and settings that differ from the setup, items outside it, agent settings that cancel each other or do nothing (the advisor with a switch that turns flag fetching off, Remote Control with a switch that makes it unavailable, an update channel with the nonessential-traffic switch, a top-level `effortLevel` that differs from the levels under `modelSettings`, `includeCoAuthoredBy` next to `attribution`, `auto` or `bypassPermissions` in a project or local file, `cleanupPeriodDays` below 30 against the Sessions board, switches that count as set with `0` or `false`, OpenTelemetry variables in a project `env`, a Codex project `notify`, `default_permissions` with `sandbox_mode`), Claude Code settings files it would skip, Codex trust entries of folders that are gone, a missing container engine, a newer skills CLI; in a project: summary or layout sections in `AGENTS.md`, overlapping skill descriptions, broken skill links, a local setup the repository still has committed; instruction files (global and project): an `@import` in `CLAUDE.md`, `CLAUDE.local.md` or a rules file whose target does not exist (file and line, imports followed up to four hops), a file over 200 lines (the memory documentation's target, with its link), skills of different scopes (project, global, enabled Claude Code plugins) whose descriptions overlap, with file and line of both; allow rules (`permissions.allow` of the user, project and local files and Codex `.rules` files), reported as a warning for a bare `Bash` (or `Bash(*)`), a wildcard program, `Bash(<shell or interpreter> *)` or the same with `-c` or `-e` (`bash`, `sh`, `python`, `node`, `npx` and similar; `Bash(python -m pytest *)` is not reported), and as information for a bare `Edit`, `Write` or `WebFetch` (or `Tool(*)`) and a `*` before the rest of the command (`Bash(git * main)`), each with scope, file, rule and how many registered repositories carry it; nothing is changed and no rule is proposed. Exit 1 on an error, see [Machine-readable output](#machine-readable-output) |
| `doctor` level line | the install level it finds (lite: the plugin, standard: a project setup too, full: the global rules too) and what the next level adds; below full only the plugin is expected |
| `settings list [--agent claude\|codex] [--advanced] [--project dir]`, `settings get <key>`, `settings set <key> <value>\|--unset\|--bundle <id> [--layer user\|project\|local]` | the agents' own settings (Claude Code `settings.json`, Codex `config.toml`): the app's list per agent with default, value and the file it comes from, notes on keys that cancel each other, and with `--advanced` every key of the pinned schemas and the settings reference plus keys the app does not know (shown and kept). A change is a plan with a diff and an undo like any other; the value is checked first (strict JSON for Claude Code, a line edit that keeps comments and key order for Codex), managed settings are never written, an environment switch is set (value `set`) or removed, never `0` or `false`, and values of names that look like secrets are never printed. `projects.<path>` with `--unset --agent codex` removes a trust entry |
| `rules list [--agent claude\|codex] [--project dir]`, `rules disable\|enable <file> [--agent a] [--project dir]` | the instruction files Claude Code and Codex load, with owner (`BenchKeeper`, `project`, `yours`), size, load state and the context budget. `disable` leaves a file out without deleting it: for Claude Code through `claudeMdExcludes` in the user settings (with `--project`: in that project's `.claude/settings.local.json`, so one project only); for a global Codex file by moving it into `<config>/disabled-rules/`, which `enable` reverses byte for byte. Both are runs, undo restores them |
| `profile export [file]`, `profile import <file>` | agents, packs, own packs and registered projects with their answers as one file (no file contents, environment values or tokens); import registers the projects found at the same paths and asks per change |
| `case add --target skill:<name>\|rule:<name> --expected <text> [--should-not]` | records an agent miss as an eval case; the prompt comes from `--run <session run>`, `--transcript`, `--query` or `--description` |
| `test [dir]` | deterministic checks, no agent session: files match the ledger, expected plugins or skill copies, nothing unexpected installed, project community skills at the library pins. Exit 1 on a failure |
| `eval [--agents a,b] [--model m] [--target t] [--all]` | trigger cases (`plugins/benchkeeper/evals/` and your own) as real agent sessions in scratch repositories; miss and false-trigger rates per skill, agent, agent version and model. Uses your subscription, asks first, refuses when `CI` is set; runs only targets whose skill or cases changed unless `--all` |

## Machine-readable output

`doctor`, `test`, `plan`, `project plan`, `history`, `projects list` and `packs list` take `--json`: one JSON document on stdout, logs and error messages on stderr. Every document has `schemaVersion` (1) and `command`; a failure has `error` instead of the other keys. Values of environment variables and file contents never appear: a change lists its title and path, not its diff.

| Command | Keys |
|---|---|
| `doctor` | `level` (install level or null), `adds`, `findings` (`level` error, warning or info, `check`, `message`, `fix`, and when they apply `tag`, `dir`, `file`, `line`, `scope`, `rule`, `repos`), `summary` (`error`, `warning`, `info`) |
| `test` | `ok`, `checks` (`name`, `ok`, `problems`) |
| `plan`, `project plan` | `agents` and `level` (plan) or `dir` (project plan), `changes` (`id`, `step`, `title`, `kind`, `destructive`, `optional`, `selected`, and when they apply `path`, `argv`, `error`); project plan also `skills` (`added`, `removed`) and `warnings` |
| `history` | `runs` (`id`, `kind`, `status`, `scope`, `time`, `changes`, and when they apply `of`, `evalCase`, `target`), `backups` |
| `projects list` | `projects` (`path`, `added`) |
| `packs list` | `packs` (`id`, `own`, `skills`, `plugins`) |

| Exit code | Meaning |
|---|---|
| 0 | clean: no finding of level error (warnings and info do not count) |
| 1 | a finding of level error (`doctor`), a failed check (`test`), a change that cannot be made (`plan`, `project plan`) |
| 2 | usage or read failure: an unknown option or command, a bad value, an unreadable file (also the registered projects file, for `doctor`, `plan` and `projects list`), `--json` on another command, and with `--json` an uncaught error |

## Web UI

`benchkeeper ui` serves on `127.0.0.1` at a free port and opens the browser with a one-time link (`--no-open` prints it). The browser gets a file only you can read, which forwards to the link, so the token stays out of process arguments other local users can see. The link's token becomes an HttpOnly, SameSite=Strict session cookie named per port (`bk_session_<port>`) and an API key that the page keeps in its own origin's storage. API requests need both: browsers send the cookie to every server on `127.0.0.1`, the key stays with this page. The sessions board frame, which cannot send a header, loads with a one-time ticket the page asks for with the key. The server rejects other Host headers, foreign or `null` origins, cross-site fetches, changes sent with GET, and API requests without the key in the `x-benchkeeper` header. It stops with Ctrl+C in its terminal or with the Stop button in the header, which the server refuses while an apply or eval runs; scans and setup suggestions still running are cancelled. Recorded agent sessions run from the CLI only. Applies, evals and setup suggestions run on the server: while one runs, the header shows it and opens its progress, also after a reload.

The view is part of the URL (`#/projects?path=<dir>`), so a reload keeps it. "Choose folder" opens the system dialog: `osascript` on macOS, `zenity`, then `kdialog` on Linux. With none of them, on Windows, on Linux without a display, or after a cancel, type the path. The server blocks other requests while the dialog is open.

| Keys | Action |
|---|---|
| Ctrl+K (macOS: Cmd+K), / | command palette: views, projects, skills, the last 20 runs, plan global setup, run doctor, toggle theme |
| Ctrl+1 to Ctrl+9 (macOS: Cmd) | the first nine views in sidebar order |
| Ctrl+J (macOS: Cmd+J) | light or dark theme |

Where the browser handles one of these keys itself, the sidebar, the palette and the header buttons do the same.

The UI is built from dev dependencies (Mantine core, charts and spotlight, Recharts, Tabler icons, the Inter font, React) into `dist/`. The published package has no extra runtime dependencies.

## Configuration

| Name | Default | Effect |
|---|---|---|
| `BENCHKEEPER_HOME` | your home directory | the home the app reads and writes; tests point it at a temporary directory |
| `BENCHKEEPER_NO_UPDATE_CHECK=1` | unset | no registry request for a newer version (it runs only in a terminal, not when `CI` is set, and never installs) |

Files below `~/.config/benchkeeper/`: `ledger/` (one JSON file per run), `backup/<run>/` (replaced and removed files), `projects.json`, `packs/`, `evals/` (own cases, `results.jsonl`, outputs of rule cases), `board.html`. Caches below `~/.cache/benchkeeper/`: `worktrees/`, `sessions.json`, `prs.json`.

In the dev container (repository `AGENTS.md`):

- `npm test`: unit tests against temporary home directories with stubbed agent commands
- `npm run smoke`: start, plan, apply and ledger write
- `npm run build && npm run test:ui`: the web UI against a fixture home, axe in light and dark mode

## Release

The package version equals the plugin version (`plugins/benchkeeper/*/plugin.json`), checked by `test/package.test.mjs`. `npm pack` copies rules, own skills, the library catalog and eval sets into `content/` and builds the UI, so `plan` and `apply` work offline for them. The owner publishes with the "npm publish" workflow (Actions, Run workflow, the version as input), which publishes through npm trusted publishing (no token) with provenance. The trusted publisher in the package's npm settings names this repository and `npm.yml`.
