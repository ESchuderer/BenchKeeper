## Iterative brief (`bench/briefs/winery-iterative/`, v1.11)

- Steps: the React winery brief (step 0), then the change requests `changes/1.md` to `changes/4.md` (group discount, staff add tastings, guests cancel with reference and email, CSV export for staff), each sent as a follow-up turn in the same session after the follow-up rule settled the previous step.
- Scoring per step: the runner scores a snapshot after each step into `checkpoints/<k>/` with the hidden tests of all steps so far (`HIDDEN_FILES`: the six feature tests and `s1` to `s<k>`, titles S1 to S4); the last step is scored into `score/` with all tests. A step passes strictly when every test that ran passed, so a regression in an earlier feature fails it. The tests are validated against a reference with all change requests and one mutant per change test (`validate.sh`).
- Code metrics per step (`bench/scorer/erosion.mjs`, TypeScript 6.0.3 parser; jscpd 5.4.0): cyclomatic complexity per function, erosion (the share of all complexity in functions above complexity 10), duplication (the share of lines in clones of 50 tokens or more), source lines; the agent's own source only (no dependencies, build output, tests or configuration).
- Conditions: an empty workspace (as the other briefs), or `SCAFFOLD=1`: the skeleton in `scaffold/` (folders, core types, function signatures, boundary notes in `docs/architecture.md`) copied in and committed before the first turn, recorded as `condition` and run in its own run directory.
- Time: one limit for all steps (`TIMEOUT`); steps not reached count as failed (`steps_sent` in `trial.json`).

### Task

- Prompt: `bench/briefs/winery-react/brief.md`, passed unchanged to every arm as the only user message. It states the product, look and feel, React with established frameworks and libraries, the run contract, and a closing process paragraph asking every arm to use its installed skills, agents, plugins and spec tool in each phase and to follow its rules. The earlier `winery`, `winery-workflow` and `winery-autonomous` briefs are outdated and kept for reference in `bench/archive/briefs/`; their results were removed by owner decision. The `winery` hidden tests, reference app and `validate.sh` stay in `bench/briefs/winery/`, shared with `winery-react`.
- Hidden tests: `bench/briefs/winery/hidden/`, one Playwright test per required feature (F1 to F6), roles and visible text from the brief only. Each feature makes its own bookings and compares seat counts with what it read, so one failing feature does not fail or skip another; a feature passes only when its test ran and passed.
- Robustness tests (`robustness.spec.mjs`, R1 to R12, run after the features): each follows from a sentence of the brief. R2 to R6 and R10 (run first) guests 0, 9 and 2.5, empty name, empty email, a name of only spaces (R10) rejected without a booking, with a field marked invalid (browser validation message or `aria-invalid="true"`, which covers validation while typing) or new text in the form's container (the shared tests check the winery wording "next to the form", not the React wording "next to the field"); R1 two simultaneous bookings for the last seats (exactly one confirmed, seats left never below zero); R7 neither `/staff` nor any URL that the signed-in staff page loaded returns booking data to a client without a session (covers the app's API); R8 a name with HTML tags is not rendered as markup on the staff page (rejecting the name with an error message also passes); R9 the app's own booking request (JSON, form-encoded or multipart), replayed without the form: a valid replay books one seat (control; an app that refuses it, for example with a CSRF or origin check, passes), then replays with guests -3 and 2.5 leave the seats unchanged (server-side checks); R11 a name with accents and another script ("Zoë Ångström-Łukasiewicz 山田") is shown exactly on the staff page; R12 the app's own cancel request, replayed without a session, frees no seats (run before R9). Reported as robustness passed (of 12), never added to the feature count.
- Test validation (`bench/briefs/winery/validate.sh`): the reference app `bench/briefs/winery/reference/` and a correct variant with other markup (table, guests dropdown, cancelled bookings kept, bound to `localhost`) pass all six; four mutants (capacity check removed, staff page open, cancel ignored, email unchecked) each fail exactly their feature while the other five pass. Result 2026-10-14: all as expected. React brief: `bench/briefs/winery-react/validate.sh` with the React single-page reference `bench/briefs/winery-react/reference/` (Express, React, Vite) and the same four mutants. Since v1.7 both scripts also run one mutant per robustness test (booking delayed between check and write, guests 0, guests 9, fractional guests, empty name, empty email accepted, bookings readable without a session while the staff page still asks for the password, names rendered as HTML, guests checked only in the browser, names of only spaces accepted, names reduced to ASCII, cancel without a session); each fails exactly its robustness test, and a feature mutant also fails the robustness test that probes the same rule (capacity: F3 and R1; staff page open: F5, R7 and R12; email unchecked: F4 and R6; empty name accepted: R5 and R10; fractional guests accepted: R4 and R9). The tests wait for network requests to settle after each submit, so asynchronous single-page apps cannot slip a booking past a check.

### Run

- Models `claude-haiku-5-5` and `claude-sonnet-5-5`, one round each for all Claude Code arms (both runs in parallel), then the OpenCode arms on both models; Opus 5.5 only if the owner decides after seeing the costs; effort `high`; one trial at a time per run; Claude Code with `--dangerously-skip-permissions`, stream-json with hook events and a debug log; OpenCode with `--auto` and `--format json`.
- One round of all 16 arms in an order shuffled with the seed (`bench/run-brief.sh`, order logged in `manifest.txt`); one trial at a time; timeout 90 minutes per trial, shared by all turns (each turn gets the remaining time). A resumed run never repeats a finished agent run and refuses to continue when an arm image changed.
- Sandbox: the agent container mounts only its empty workspace and a log directory; `bench/`, the hidden tests and other repositories are never mounted. Network is on (package installs).
- Credentials: Claude Code arms use the owner's Max subscription through `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`, environment or `~/.config/benchkeeper/oauth-token`); OpenCode arms use an Anthropic API key (`ANTHROPIC_API_KEY` or `~/.config/benchkeeper/anthropic-api-key`); each container gets only its runtime's credential; never written to results. After each trial the runner searches the trial directory for the token and stops if it finds it.
- Follow-up rule: when the agent ends a turn and the app does not run (a `start` script, and `npm install`, `npm run build --if-present` and `npm start` serve the start page within 20 s, checked in the agent's container on a copy of the workspace), or its final message waits for confirmation (last line a question, or a phrase such as "once you confirm" or "shall I continue" in its last five lines), the runner continues the same session with the fixed message "Continue until the brief is fully implemented and npm start runs the app. Do not wait for approval.", at most twice, within the trial's 90 minutes. The number of follow-ups is recorded per trial; finishing without one is reported separately.
- Commands: `bench/run-brief.sh winery-react claude-haiku-5-5 high 1 41` and `bench/run-brief.sh winery-react claude-sonnet-5-5 high 1 41` (arms A to P); the OpenCode arms with the same commands and arms `"Q R S T U"`.

### Checks before a run

Before each run: every image builds, and an unauthenticated start shows the arm's plugins, markers and MCP servers (the delivery audit on the recorded fixtures, `bench/scripts/fixtures/`); for arms with BenchKeeper rules, a probe per image (list the headings of the loaded `~/.claude/rules/` files, no tools) shows the expected rules.

### Scoring (`bench/scorer/score.sh`, `bench/scripts/trial.mjs`)

Per trial, in a copy of the workspace, in pinned containers:
- `npm install`, `npm run build --if-present`, `npm start` with `PORT` and a random `STAFF_PASSWORD`;
- hidden features passed (of 6); robustness tests passed (of 12, `robustness_passed`); mutation score of the agent's own tests (`mutation`: killed and timed-out mutants over all counted mutants, Stryker 10.0.0 command runner rerunning `npx vitest run` or `npm test` per mutant, text literals not mutated, on a copy of the workspace, 45 minutes per app; `null` with a reason when it cannot run); axe violations (WCAG 2.2 AA tags) on start, form, confirmation and staff pages; Lighthouse performance, accessibility and best practices on the start page; `npm audit` counts; the agent's own `npm test` exit code (in the node base image without browsers);
- non-blank source and test lines;
- maintenance facts from the workspace (`maintenance` in `trial.json`): README, README with install and start steps, lockfile, test script, lint or type-check script, CI workflow, pinned Node version, changelog, docs or specs;
- wall-clock minutes; from the transcript (last result per session, since follow-up turns continue the session and its totals are cumulative): turns, tokens, API-equivalent USD (`total_cost_usd`; not billed), whether the run ended with a question;
- captured for manual comparison: the built app as delivered (`app.tar.gz`: source and git history, without `node_modules`) and full-page screenshots of the start, form, confirmation and staff pages;
- workflow trace: Skill and Agent calls, plan or spec files written, tests written and whether before the first source file, whether a review step ran, the last tool call.

### Per-phase measurements (`bench/scripts/phases.mjs`, runs with `PHASES=1`)

Each model call is assigned a phase from what it does, independent of skill names: spec (writes to spec, plan, design, proposal, tasks or ADR files; skills like brainstorm, grill, propose, plan), test (writes to test files; TDD skills), build (other writes; install and build commands; apply and implement skills), verify (test, lint and type-check commands, Playwright MCP; verification skills), review (review and security agents and skills); calls that only read keep the previous phase. Per phase and per subagent type: calls, minutes and cost. Claude Code: cost is the trial total split by each call's token weight (input 1, cache write 1.25, cache read 0.1, output 5, output estimated from content length), time from the event timestamps; OpenCode: cost and time per message as reported. Observational and approximate: it shows where time and cost go, not what causes quality.

### App review (`bench/review/`)

Each built app is reviewed blind by Claude Opus 5.5 (effort `high`) with the fixed prompt `bench/review/app-review.md` and schema `bench/review/schema.json`: headless in the stock arm-A image, read-only, tools limited to Read, Glob and Grep; inputs are the brief, the app source filtered inside a container (kept: code, tests, build and CI configuration, README, docs, ADRs and living specs in `openspec/specs` or `specs/`, which a later maintainer reads; removed: dependencies, agent tooling and process files such as `.claude`, `.opencode`, `.specify`, `.mcp.json`, the project-setup devcontainer, `AGENTS.md`, `CLAUDE.md`, skills locks, `openspec/changes`, `.scratch`, `docs/superpowers`, `docs/agents`, `.git`) and the four screenshots; no hidden-test scores. The reviewer image ID is recorded in `review.json`. Known leaks: code-level traces such as Ponytail's `shortcut:` comments or a framework's coding style, and kept specs or ADRs, can hint at the arm; specs and ADRs stay because they are maintenance documentation. Thirteen criteria rated 1 to 5 with evidence (requirements, correctness, security, code quality, tests, UX and design, accessibility, simplicity, maintainability: could a developer pick the app up again later from the repository alone: setup instructions, regression tests, build and CI, release approach, documentation, pinned versions; visual design, layout, usability, and reception: how the brief's audience would receive the app on a first visit), an overall rating from 1 to 10, strengths, issues and a verdict (`review.json` per trial). A model judge is a signal with known biases (for example toward longer or more polished output), reported next to the automated scores, never instead of them.

### Validity

- Delivery audit (`trial.mjs`): every init event (first turn, follow-ups, resumes after a background agent) lists exactly the arm's plugins, marker skills or agents and connected MCP servers (BenchKeeper layer: `playwright`; others: none), none of another arm's markers, and the session's first turn (`SessionStart:startup`) shows the expected hook output (a follow-up resumes the session, and Superpowers' hook does not fire on resume); arms without hooks show none. A failed audit invalidates the trial.
- A trial stopped by a usage limit, API overload or an authentication failure is an infrastructure error: rerun once (delete its directory and rerun the command), then listed as excluded.
- Every trial is reported, including stalls, trials without code and invalid ones.

### Report

`bench/results/<date>-<brief>-<model>.md`: setup (versions, image IDs, model, effort, seed, order), the data copied by `bench/publish.sh` (manifest, per trial `trial.json`, transcript, `app.tar.gz`, screenshots), the per-arm table from `bench/scripts/summary.mjs` (median and range over 3 trials, no significance tests), per-trial workflow traces, exclusions, deviations from this protocol, subscription usage read before and after.

### Limitations

- One brief, one trial per arm and model: descriptive only; differences between arms are anecdotal.
- Whole-stack arms: workflow traces show what co-occurs with better scores, not what causes it.
- Effects change by model; Haiku results say little about Sonnet.
- The process paragraph in the brief asks every arm for its process; results describe prompted behavior, not what an unprompted request gets.
- Exact labels in the brief favor arms that follow the copy literally; all arms get the same brief.
- `tests_first` compares the first test file write with the first source file write (edit tools and shell writes such as `cat > f`); test code inside source files and files created by scaffolders are not detected.
- The agent's own browser tests fail in the scorer's node image; their exit code is informational.

## Cartridges brief: static app, 2D drawings, print, on Claude Haiku 5.5, then Sonnet 5.5

Purpose: a second brief that tests presentation, a print view and computed technical drawings instead of a server app. Owner decision 2026-10-15 (#31): all 29 arms, Haiku first, then Sonnet, after the Sonnet winery-react runners finish. Everything not listed here is as in the winery-react pre-screen above.

### Task

- Prompt: `bench/briefs/cartridges/brief.md`: a static reference database of 25 C.I.P. cartridges with a detail view, a 2D drawing (outside view and section, dimensions, title block) and a one-page A4 print view, in plain HTML, CSS and JavaScript that works from `file://`. It carries the display format, nine geometry rules derived from OpenBallistics' `lib/shapes2d/case.ts` and `bullet.ts`, the same closing process paragraph as winery-react, and the 25 records as JSON Lines, pinned to OpenBallistics commit `e83db43` (https://github.com/PiMetry/OpenBallistics, MIT).
- Selection of the 25: no published popularity ranking of C.I.P. cartridges exists. They are widely used hunting, sport and handgun cartridges, chosen to cover every metallic family and drawing rule: 12 rimless, 2 belted, 2 rimmed, 6 pistol, 3 rimfire. Shotshells are excluded because hull geometry needs different rules.
- Hidden tests: `bench/briefs/cartridges/hidden/`, C1 to C6: list (25 names, count), search by alternative name and family filter, detail values (units, tolerance, angle format), drawing (accessible name, L3 and L6 with values, viewBox in mm), print (controls hidden, one A4 page for 308 Win. and 9,3 x 74 R), offline (`file://`, no `http(s)` or `ws(s)` request) with an address per detail view that survives a reload. Drawing quality and proportions are left to the app review.
- Test validation (`bench/briefs/cartridges/validate.sh`): the reference app `bench/briefs/cartridges/reference/` (data built from `brief.md`) and a correct variant with other markup (list as a table, drawing named by `<title>`, symbols as plain cells) pass all six; five mutants each fail exactly their feature: search ignores alternative names (C2), no L6 dimension (C4), print stylesheet removed (C5), scripts loaded as ES modules (C6), no address per detail view (C6). Result 2026-10-15: all as expected; `bench/briefs/winery/validate.sh` and `bench/briefs/winery-react/validate.sh` with the changed scorer: unchanged, all as expected.

### Run and scoring differences

- Settings `bench/briefs/cartridges/brief.json`: `"serve": "static"`.
- Scorer: no `npm start`, `npm run build` or `STAFF_PASSWORD`; `npm install` and `npm audit` only when the workspace has a `package.json` (for the agent's own tests). The workspace copy is served by `bench/scorer/static.mjs` (Node standard library) for Lighthouse and C1 to C5, and mounted read-only for C6.
- Follow-up rule: the app runs when `index.html` in the workspace root loads from `file://` without page errors (`bench/scorer/opens.mjs`, in the pinned Playwright image on a copy of the workspace). Message: "Continue until the brief is fully implemented and index.html opens the app from disk. Do not wait for approval."
- axe pages: `list` and the six detail views below.
- Screenshots: `list.jpg`; `detail-<key>.jpg` for 308_win, 300_win_mag, 9_3_x_74_r, 9_mm_luger, 22_long_rifle, 44_rem_mag; `print-308_win.jpg` (print media, A4 width).
- App review: prompt `bench/briefs/cartridges/review.md`, the same thirteen criteria, overall rating and `schema.json`, worded for this brief (drawing rules under requirements and correctness; HTML injection and external requests under security). Extra input: OpenBallistics reference drawings (`bench/briefs/cartridges/review-refs/`, rendered with `rsvg-convert -w 1600` from `fixtures/rendering/samples/<key>.drawing.landscape.svg` at commit `e83db43`) for 308_win, 300_win_mag, 9_mm_luger and 22_long_rifle; where they differ from the brief's rules, the brief wins.
- Commands: `bench/run-brief.sh cartridges claude-haiku-5-5 high 1 41 "<arms>"`, then the same with `claude-sonnet-5-5`, three runners per model with the arm partition of the winery-react Sonnet run; then `bench/review/review.sh bench/briefs/cartridges <trial-dir>` per trial, billed to the subscription (`REVIEW_AUTH` unset), never the API key.

### Limitations

- The geometry rules are simplified (no boat tails, crimps or cannelures; primer pocket diameters and bullet shape factors are conventions of the brief, not C.I.P. data).
- The maintenance fact "README with install and start steps" looks for `npm install` and `npm start`; a static app documents opening `index.html` instead, so this fact is not comparable with the winery briefs.

## Brownfield brief (`bench/briefs/openballistics/`, v1.13)

Purpose: work in an existing codebase over several steps: reuse its code, keep its tests green, follow its conventions and the setup an earlier step wrote. Everything not listed here is as in the winery-react pre-screen.

- Baseline (`prepare.sh`, needs network): PiMetry/OpenBallistics (https://github.com/PiMetry/OpenBallistics, MIT) at `e83db43`, `.github/workflows/` removed, `README.md` reduced to its title, a fresh repository with one commit `chore: baseline` (fixed author and date) and no remote, plus an empty `lib/data/.gitkeep`: the pinned commit deleted `lib/data`, and `site/src/lib/boundaries.test.ts` fails without it, so the suite would be red before any step. Built once per run (`<run>/baseline`, its commit in `manifest.txt`) and copied into every trial, so all arms start from the same commit.
- Project template: arms with a project (BenchKeeper layer, spec tools) get only the template files the baseline does not have (`cp -an`), committed as `chore: project setup` after the baseline. At `e83db43` no template file exists in the baseline, so nothing is skipped. The `condition` is `baseline`.
- Steps: `steps/1.md` repository setup (CI, Pages deployment, README, versioning and release, changelog, dependency updates, commit convention; written, not run), `steps/2.md` a compare view of two cartridges, `steps/3.md` a fixed reviewer comment (one bug, one style point). Each step is a new session (no `--continue`, Claude Code and OpenCode); the follow-up rule applies within the step's session. Settings `brief.json`: `"serve": "none"` (the repository has no `start` script, so no app check: only a final message that waits fires a follow-up), message "Continue until the task of this step is complete in the repository. Do not wait for approval.". One time limit for all steps (`TIMEOUT`); a step not reached has no `steps/<k>/`.
- Recorded per step (`steps/<k>/`): start and end, the usage gate reading (5-hour and weekly utilization and resets) before and after (Claude Code arms), whether the first turn's final message waited, follow-ups, the step's transcript lines, and a snapshot `repo.tar.gz` (with `.git`, without `node_modules`); `base.tar.gz` is the state before step 1.
