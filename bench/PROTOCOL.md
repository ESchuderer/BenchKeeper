## Iterative brief (`bench/briefs/winery-iterative/`, v1.11)

- Steps: the React winery brief (step 0), then the change requests `changes/1.md` to `changes/4.md` (group discount, staff add tastings, guests cancel with reference and email, CSV export for staff), each sent as a follow-up turn in the same session after the follow-up rule settled the previous step.
- Scoring per step: the runner scores a snapshot after each step into `checkpoints/<k>/` with the hidden tests of all steps so far (`HIDDEN_FILES`: the six feature tests and `s1` to `s<k>`, titles S1 to S4). The last step is scored into `score/` with all tests. A step passes strictly when every test that ran passed, so a regression in an earlier feature fails it. The tests are validated against a reference with all change requests and one mutant per change test (`validate.sh`).
- Code metrics per step (`bench/scorer/erosion.mjs`, TypeScript 6.0.3 parser; jscpd 5.4.0): cyclomatic complexity per function, erosion (the share of all complexity in functions above complexity 10), duplication (the share of lines in clones of 50 tokens or more), source lines. The agent's own source only (no dependencies, build output, tests or configuration).
- Conditions: an empty workspace (as the other briefs), or `SCAFFOLD=1`: the skeleton in `scaffold/` (folders, core types, function signatures, boundary notes in `docs/architecture.md`) copied in and committed before the first turn, recorded as `condition` and run in its own run directory.
- Time: one limit for all steps (`TIMEOUT`). Steps not reached count as failed (`steps_sent` in `trial.json`).

### Task

- Prompt: `bench/briefs/winery-react/brief.md`, passed unchanged to every arm as the only user message. It states the product, look and feel, React with established frameworks and libraries, the run contract, and a closing process paragraph asking every arm to use its installed skills, agents, plugins and spec tool in each phase and to follow its rules. The earlier `winery`, `winery-workflow` and `winery-autonomous` briefs are outdated and kept for reference in `bench/archive/briefs/`. Their results were removed by owner decision. The `winery` hidden tests, reference app and `validate.sh` stay in `bench/briefs/winery/`, shared with `winery-react`.
- Hidden tests: `bench/briefs/winery/hidden/`, one Playwright test per required feature (F1 to F6), roles and visible text from the brief only. Each feature makes its own bookings and compares seat counts with what it read, so one failing feature does not fail or skip another. A feature passes only when its test ran and passed.
- Robustness tests (`robustness.spec.mjs`, R1 to R12, run after the features): each follows from a sentence of the brief. R2 to R6 and R10 (run first) guests 0, 9 and 2.5, empty name, empty email, a name of only spaces (R10) rejected without a booking, with a field marked invalid (browser validation message or `aria-invalid="true"`, which covers validation while typing) or new text in the form's container (the shared tests check the winery wording "next to the form", not the React wording "next to the field"). R1 two simultaneous bookings for the last seats (exactly one confirmed, seats left never below zero). R7 neither `/staff` nor any URL that the signed-in staff page loaded returns booking data to a client without a session (covers the app's API). R8 a name with HTML tags is not rendered as markup on the staff page (rejecting the name with an error message also passes). R9 the app's own booking request (JSON, form-encoded or multipart), replayed without the form: a valid replay books one seat (control; an app that refuses it, for example with a CSRF or origin check, passes), then replays with guests -3 and 2.5 leave the seats unchanged (server-side checks). R11 a name with accents and another script ("Zoë Ångström-Łukasiewicz 山田") is shown exactly on the staff page. R12 the app's own cancel request, replayed without a session, frees no seats (run before R9). Reported as robustness passed (of 12), never added to the feature count.
- Test validation (`bench/briefs/winery/validate.sh`): the reference app `bench/briefs/winery/reference/` and a correct variant with other markup (table, guests dropdown, cancelled bookings kept, bound to `localhost`) pass all six. Four mutants (capacity check removed, staff page open, cancel ignored, email unchecked) each fail exactly their feature while the other five pass. Result 2026-10-14: all as expected. React brief: `bench/briefs/winery-react/validate.sh` with the React single-page reference `bench/briefs/winery-react/reference/` (Express, React, Vite) and the same four mutants. Since v1.7 both scripts also run one mutant per robustness test (booking delayed between check and write, guests 0, guests 9, fractional guests, empty name, empty email accepted, bookings readable without a session while the staff page still asks for the password, names rendered as HTML, guests checked only in the browser, names of only spaces accepted, names reduced to ASCII, cancel without a session). Each fails exactly its robustness test, and a feature mutant also fails the robustness test that probes the same rule (capacity: F3 and R1; staff page open: F5, R7 and R12; email unchecked: F4 and R6, empty name accepted: R5 and R10, fractional guests accepted: R4 and R9). The tests wait for network requests to settle after each submit, so asynchronous single-page apps cannot slip a booking past a check.

### Run

- Model `claude-sonnet-5-5`, Claude Code arms only (1.15, 1.16). The recorded runs used `claude-haiku-5-5` and `claude-sonnet-5-5`, one round each for all Claude Code arms (both runs in parallel), then the OpenCode arms on both models (OpenCode with `--auto` and `--format json`). Effort `high`, one trial at a time per run, Claude Code with `--dangerously-skip-permissions`, stream-json with hook events and a debug log.
- One round of all 24 Claude Code arms (the recorded runs: 29 arms with the OpenCode arms) in an order shuffled with the seed (`bench/run-brief.sh`, order logged in `manifest.txt`). One trial at a time. Timeout 90 minutes per trial, shared by all turns (each turn gets the remaining time). A resumed run never repeats a finished agent run and refuses to continue when an arm image changed.
- Sandbox: the agent container mounts only its empty workspace and a log directory. `bench/`, the hidden tests and other repositories are never mounted. Network is on (package installs).
- Credentials: Claude Code arms use the owner's Max subscription through `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`, environment or `~/.config/benchkeeper/oauth-token`). The recorded OpenCode arms used an Anthropic API key (`ANTHROPIC_API_KEY` or `~/.config/benchkeeper/anthropic-api-key`). Each container gets only its runtime's credential, never written to results. After each trial the runner searches the trial directory for the token and stops if it finds it.
- Follow-up rule: the runner continues the same session with the fixed message "Continue until the brief is fully implemented and npm start runs the app. Do not wait for approval." when the agent ends a turn and the app does not run, or its final message waits for confirmation. At most twice, within the trial's 90 minutes. The app runs when it has a `start` script and `npm install`, `npm run build --if-present` and `npm start` serve the start page within 20 s (checked in the agent's container on a copy of the workspace). A final message waits when its last line is a question or its last five lines contain a phrase such as "once you confirm" or "shall I continue". The number of follow-ups is recorded per trial. Finishing without one is reported separately.
- Command: `bench/run-brief.sh winery-react claude-sonnet-5-5 high 1 41` per runner with its arms as the sixth argument (`"<arms>"`), which replaces the default list A to P and V to Y. The default leaves out AB, AC, AD and AE (`"AD AE"` runs layer v3). The recorded runs also ran `claude-haiku-5-5` and the OpenCode arms with the same commands.

### Checks before a run

Before each run: every image builds, and an unauthenticated start shows the arm's plugins, markers and MCP servers (the delivery audit on the recorded fixtures, `bench/scripts/fixtures/`). For arms with BenchKeeper rules, a probe per image (list the headings of the loaded `~/.claude/rules/` files, no tools) shows the expected rules.

### Scoring (`bench/scorer/score.sh`, `bench/scripts/trial.mjs`)

Per trial, in a copy of the workspace, in pinned containers:
- `npm install`, `npm run build --if-present`, `npm start` with `PORT` and a random `STAFF_PASSWORD`
- hidden features passed (of 6)
- robustness tests passed (of 12, `robustness_passed`)
- mutation score of the agent's own tests (`mutation`): killed and timed-out mutants over all counted mutants. Stryker 10.0.0 command runner rerunning `npx vitest run` or `npm test` per mutant, text literals not mutated, on a copy of the workspace, 45 minutes per app. `MUTATION_CPUS` caps the container's CPUs and Stryker's test runners (default: no CPU cap, 8 runners). `null` with a reason when it cannot run
- axe violations (WCAG 2.2 AA tags) on start, form, confirmation and staff pages
- Lighthouse performance, accessibility and best practices on the start page
- `npm audit` counts
- the agent's own `npm test` exit code (in the node base image without browsers)
- non-blank source and test lines
- maintenance facts from the workspace (`maintenance` in `trial.json`): README, README with install and start steps, lockfile, test script, lint or type-check script, CI workflow, pinned Node version, changelog, docs or specs
- wall-clock minutes
- from the transcript (last result per session, since follow-up turns continue the session and its totals are cumulative): turns, tokens, API-equivalent USD (`total_cost_usd`, not billed), whether the run ended with a question
- captured for manual comparison: the built app as delivered (`app.tar.gz`: source and git history, without `node_modules`) and full-page screenshots of the start, form, confirmation and staff pages
- workflow trace: Skill and Agent calls, plan or spec files written, tests written and whether before the first source file, whether a review step ran, the last tool call.

### Per-phase measurements (`bench/scripts/phases.mjs`, runs with `PHASES=1`)

Each model call is assigned a phase from what it does, independent of skill names: spec (writes to spec, plan, design, proposal, tasks or ADR files; skills like brainstorm, grill, propose, plan), test (writes to test files; TDD skills), build (other writes; install and build commands; apply and implement skills), verify (test, lint and type-check commands, Playwright MCP; verification skills), review (review and security agents and skills). Calls that only read keep the previous phase. Per phase and per subagent type: calls, minutes and cost. Claude Code: cost is the trial total split by each call's token weight (input 1, cache write 1.25, cache read 0.1, output 5, output estimated from content length), time from the event timestamps. Recorded OpenCode runs: cost and time per message as reported. Observational and approximate: it shows where time and cost go, not what causes quality.

### App review (`bench/review/`)

Each built app is reviewed blind by Claude Opus 5.5 (effort `high`) with the fixed prompt `bench/review/app-review.md` and schema `bench/review/schema.json`: headless in the stock arm-A image, read-only, tools limited to Read, Glob and Grep. Inputs are the brief, the app source filtered inside a container (kept: code, tests, build and CI configuration, README, docs, ADRs and living specs in `openspec/specs` or `specs/`, which a later maintainer reads; removed: dependencies, agent tooling and process files such as `.claude`, `.opencode`, `.specify`, `.mcp.json`, the project-setup devcontainer, `AGENTS.md`, `CLAUDE.md`, skills locks, `openspec/changes`, `.scratch`, `docs/superpowers`, `docs/agents`, `.git`) and the four screenshots. No hidden-test scores. The reviewer image ID is recorded in `review.json`. Known leaks: code-level traces such as Ponytail's `shortcut:` comments or a framework's coding style, and kept specs or ADRs, can hint at the arm. Specs and ADRs stay because they are maintenance documentation. Thirteen criteria rated 1 to 5 with evidence (requirements, correctness, security, code quality, tests, UX and design, accessibility, simplicity, maintainability: could a developer pick the app up again later from the repository alone: setup instructions, regression tests, build and CI, release approach, documentation, pinned versions; visual design, layout, usability, and reception: how the brief's audience would receive the app on a first visit), an overall rating from 1 to 10, strengths, issues and a verdict (`review.json` per trial). A model judge is a signal with known biases (for example toward longer or more polished output), reported next to the automated scores, never instead of them.

### Validity

- Delivery audit (`trial.mjs`): every init event (first turn, follow-ups, resumes after a background agent) lists exactly the arm's plugins, marker skills or agents and connected MCP servers (BenchKeeper layer: `playwright`, others: none), and none of another arm's markers. The session's first turn (`SessionStart:startup`) shows the expected hook output (a follow-up resumes the session, and Superpowers' hook does not fire on resume). Arms without hooks show none. A failed audit invalidates the trial.
- A trial stopped by a usage limit, API overload or an authentication failure is an infrastructure error: rerun once (delete its directory and rerun the command), then listed as excluded.
- Every trial is reported, including stalls, trials without code and invalid ones.

### Report

`bench/results/<date>-<brief>-<model>.md`:

- setup (versions, image IDs, model, effort, seed, order)
- the data copied by `bench/publish.sh` (manifest, per trial `trial.json`, transcript, `app.tar.gz`, screenshots)
- the per-arm table from `bench/scripts/summary.mjs` (median and range over the trials of each arm, one trial per arm in the recorded runs, no significance tests)
- per-trial workflow traces, exclusions, deviations from this protocol, subscription usage read before and after.

### Limitations

- One brief, one trial per arm and model: descriptive only. Differences between arms are anecdotal.
- Whole-stack arms: workflow traces show what co-occurs with better scores, not what causes it.
- Effects change by model: the recorded Haiku results say little about Sonnet.
- The process paragraph in the brief asks every arm for its process. Results describe prompted behavior, not what an unprompted request gets.
- Exact labels in the brief favor arms that follow the copy literally. All arms get the same brief.
- `tests_first` compares the first test file write with the first source file write (edit tools and shell writes such as `cat > f`). Test code inside source files and files created by scaffolders are not detected.
- The agent's own browser tests fail in the scorer's node image. Their exit code is informational.

## Brownfield method (v1.13)

Purpose: work in an existing codebase over several steps: reuse its code, keep its tests green, follow its conventions and the setup an earlier step wrote. Everything not listed here is as in the common method. Each brief sets its baseline, steps, checks, review and score.

- Baseline (`prepare.sh`, needs network): a repository at a pinned commit, built once per run (`<run>/baseline`, its commit in `manifest.txt`) and copied into every trial, so all arms start from the same commit.
- Project template: arms with a project (BenchKeeper layer, spec tools) get only the template files the baseline does not have (`cp -an`), committed as `chore: project setup` after the baseline. The `condition` is `baseline`.
- Steps (`steps/<k>.md`): each step is a new session (no `--continue`). The follow-up rule applies within the step's session. Settings `brief.json`: `"serve": "none"` (no app check: only a final message that waits fires a follow-up), message "Continue until the task of this step is complete in the repository. Do not wait for approval.". One time limit for all steps (`TIMEOUT`). A step not reached has no `steps/<k>/`.
- Recorded per step (`steps/<k>/`): start and end, the usage gate reading (5-hour and weekly utilization and resets) before and after (Claude Code arms), whether the first turn's final message waited, follow-ups, the step's transcript lines, and a snapshot `repo.tar.gz` (with `.git`, without `node_modules`). `base.tar.gz` Is the state before step 1.
- Scoring (`bench/scorer/score.sh` after the trial, on each step's snapshot, `bench/rescore.sh` reruns it): `checks/step<k>.sh`, then `checks/suite.sh` (`npm ci`, `npm test`, pinned `node:22.23.3-bookworm-slim`, 20 minutes). `score.sh` runs no install, build, `npm start`, code metrics or mutation score. It writes `app.tar.gz` and `hidden.sha256` (over `hidden/` and `checks/`). Results: `steps` in `trial.json`, per step the checks (id, ok), passed of the checkable ones, suite ok, minutes, waited, follow-ups, `AskUserQuestion` calls, cost, tokens and usage.
- Cost per step: API-equivalent USD and tokens from the step's transcript lines (Claude Code arms), minutes, and the share of the 5-hour and weekly limits (utilization after minus before, null when a window reset in between or a reading failed). The share is attributable to the step only while no other runner or session uses the subscription. Each reading is one one-word Haiku request.
- Run: k of at least 3 rounds per arm and model, arm order shuffled per round with the seed. Paired comparison: within each round all arms start from the same baseline commit, so differences are taken per round and reported as median and range (no significance tests at this k). Commands: `bench/run-brief.sh <brief> <model> high 3 <seed> "<arms>"`, then `bench/review/review.sh bench/briefs/<brief> <trial-dir>` per trial.
- Limitations: the checks see each step's snapshot, uncommitted files included. The subscription share is noisy for short steps and invalid with parallel runners.

## Mistreevous brief (`bench/briefs/mistreevous/`, v1.21)

Purpose: a feature with design work in an existing library, where planning, spec, test-first, review and documentation skills apply, so the stacks' skills have a reason to run. Everything not listed here is as in the brownfield brief.

- Baseline (`prepare.sh`, needs network): nikkorn/mistreevous (https://github.com/nikkorn/mistreevous, MIT, TypeScript, 307 tests, `npm test` runs lint, build with type checking and mocha in about 5 s) at `026f1ff`, unchanged, as a fresh repository with one commit (branch `master`, fixed author and date). `prepare.sh` stops when the commit differs from `baseline.sha`.
- Steps (`steps/<k>.md`, each a new session): 1. `snapshot()` and `restore()` of a tree's execution state, from the repository's open issue [#120](https://github.com/nikkorn/mistreevous/issues/120), with the API and the state to keep stated; 2. restore checks that the snapshot belongs to the tree's definition (MDSL and equivalent JSON count as the same), rejects input that is not a snapshot, and restarts an action whose promise was pending; 3. two bug reports: `restore()` must not call `onNodeStateChange`, and snapshots must be independent of the tree. Every step lists the repository's way of working (plan before code, test-first, `npm test`, a self-review, README, Version History and package version, focused commits) and names no tool.
- Hidden tests (`hidden/step<k>.spec.ts`, mocha with chai and sinon, through the repository's ts-node in transpile-only mode, public API only, every snapshot through `JSON.stringify` and `JSON.parse`): one check per top-level describe. Step 1: `S1-api`, `S1-resume`, `S1-counters`, `S1-random`, `S1-wait-clock`, `S1-wait-delta`, `S1-details`, `S1-fresh-run`. Step 2: `S2-reject`, `S2-unchanged`, `S2-equivalent`, `S2-invalid`, `S2-async`, `S2-regressions` (step 1 tests pass). Step 3: `S3-no-events`, `S3-detached`, `S3-regressions` (steps 1 and 2 pass). Install with the network, tests without it.
- Static checks (`checks/static.mjs`, against the snapshot before the step, ids `Q<k>-*`): `tests` (test cases added in `test/`), `intact` (no test file or case removed, no `.skip`, `.only` or `x` prefix added), `deps` (dependencies unchanged), `docs` (steps 1 and 2: the README changed and documents `snapshot()` and `restore()`), `history` (a new Version History row and a changed package version), `committed` (new commits, no uncommitted tracked changes). `erosion` (`checks/erosion-check.mjs`, every step: the erosion of `src/` from `bench/scorer/erosion.mjs`, the share of complexity in functions above complexity 10 as SlopCodeBench measures it, rises by at most 0.01 over the step; baseline 0.193, reference 0.184; added 2026-10-18 before the Sonnet run).
- Suite (`checks/suite.sh`): `npm ci` and `npm test` per step.
- Process checks, from each step's workflow trace (`trial.mjs`, main thread and subagents): `plan_first` (steps 1 and 2: a plan or spec file, a spec tool's artifacts, a planning skill, a planning agent or plan mode before the first source edit), `tests_first` (a test file written before the first source file), `review` (a review skill or agent), `verified` (a test, build, lint or type check command after the last source edit). They measure what the stacks promise, for every arm alike.
- Review (`bench/review/review.sh`, Opus 5.5 at effort high, two reviews): prompt `review.md`, schema `schema.json`, eight criteria 1 to 5 (`s1_requirements`, `s1_correctness`, `s2_validation`, `s3_fixes`, `design`, `tests`, `docs`, `process`), overall 1 to 10.
- Score (`bench/scripts/brownfield-score.mjs` with the `score` block of `brief.json`): 0 to 100 per trial. Hidden checks passed of 17: 35. Suite green per step: 10. Static checks passed of 20: 15. Process checks met of 11: 15. Review criteria mapped from 1 to 5 onto 0 to 1, mean over both reviews: 25. A step not reached counts all its checks as failed. Minutes, tokens and the skills called per step are reported, not scored. No mutation testing.
- Arms: A, B, F, G, H, V, AF, AB, AC and AL (owner decision 2026-10-18). A pilot on Haiku 5.5 at k = 1 checks the brief, the audit and that each stack's skills are called; the run is Sonnet 5.5 at effort high, k = 3.
- Validation (`validate.sh`): the untouched baseline fails every step 1 hidden check; a reference trial (`reference/` in step 1, a README note, tests and a Version History row per step) passes every check of every step and the suite.
- Limitations: the process checks read tool calls, so a plan kept only in the conversation does not count. The hidden tests fix the method names `snapshot` and `restore`. Step 3's reports can describe bugs an arm's step 1 did not have; its checks then pass without a change.

## External benchmark pilot: SlopCodeBench (v1.23)

Purpose: measure solution correctness and repeatability under natural skill selection. No SCB results are recorded. Issue #112 remains deferred. The first plumbing pilot uses Claude Sonnet 5.5, effort high, arms A, AO, B and F, k = 1. AO replaces AL only in this unrun comparison. A comparative run needs repeated matched rounds (at least 5 per arm), the same problems and seed, and shuffled arm order. Report every round, medians and ranges. Two selected problems cannot establish a general stack ranking, and k = 1 cannot estimate variability.

- Sources: [harness at 31ceea3](https://github.com/SprocketLab/slop-code-bench/tree/31ceea3add480edb33431e70475c4c70597e6b31), [problems at 9cd9ca3](https://github.com/gabeorlanski/scb-problems/tree/9cd9ca3a51c3d3e2a99d2488a25baf73a2204451). `scb-xjq` has 5 checkpoints and `scb-mvvault` has 6. Each checkpoint gets a new session on the same workspace. The starting repository is empty, plus the arm's project template. Specs, tests and canaries stay in ignored caches, outside the published repository.
- Prompt condition `natural`: the harness's just-solve prompt and checkpoint specification, with Python entrypoint and requirements instructions. No added planning, test-first, review, tier or skill-use request. The fixed completion follow-up still applies to every arm. This uses our podman runner, timeout and follow-up rules, so it is not an upstream leaderboard reproduction.
- AO pins setup-v5.3 in `arms/bk-v8/`, Matt Pocock's plugin and project tracker templates, Ponytail and find-skills. Settings match AM, including the Opus advisor and Sonnet subagents. Model usage must include these models. The plugin library catalog is available to the setup skill but is not automatically installed as project skills. This arm measures the global workflow setup, not a fully customized project, host tooling or interactive setup. Historical AL, AM and AN remain separately identifiable.
- Delivery and use are separate. Every process must pass the plugin, skill-marker, MCP and hook audit. `workflow.available_skills` records init listings, `skills` records Skill tool invocations, and `skill_errors` records errors returned for those calls. A listed skill is not proof its instructions were followed. A missing call is not proof frontmatter rejected it: direct file reads, user-only invocation, relevance and description budgets also affect discovery ([Claude skill discovery](https://code.claude.com/docs/en/skills)). Do not force every skill or exclude trials for non-use.
- `workflow.tiers` records explicit main-thread `Tier:` lines, including quick, standard, full and research. Missing evidence is reported as `not observed`, not as an incorrect choice. SCB does not provide expected workflow tiers, and its two incremental tasks cannot test coverage of every tier. Python source and test edits, recognized shell writes, plan-before-code and checks-after-code use the same ordering rules as JavaScript. These are trace heuristics, not proof of TDD or review quality.
- Before a trial, `inputs.sha256` records the natural condition, model, effort, timeout, exact scorer image ID, problem pin, generated prompts, runner, parser, shared scorer source and problem files. Resuming with changed inputs fails. Each arm runs by its inspected image ID, checked against the first manifest entry. Publish the input manifest and each trial's fingerprint. A seed fixes arm order, not model output. Provider changes, concurrency, network dependency resolution and model sampling remain sources of variation.
- Scoring uses `slop-code eval-snapshot` and `scb-check` 0.1.3 in the pinned scorer image. Each populated Core, Functionality, Error and Regression group passes only when all its tests pass. Absent groups are null. The upstream checkpoint config controls prior tests: mvvault checkpoint 6 explicitly disables them, so its Regression group is null. Raw per-group test counts, test-collection hash, command exits, scorer image ID, verbosity and erosion are retained in `steps[].scb` and published in `trial.json`. `summary.mjs` reports per-trial counts and quality next to the group checks. No composite SCB score.
- Failed evaluation commands, missing or malformed counts, upstream infrastructure failures and incomplete pytest execution are scoring errors, not failed solutions. Missing or failed delivery audits, agent infrastructure errors and checkpoint scoring errors exclude a trial from summaries, score CLIs and site rankings. Counts and exclusion reasons remain visible in CLI output and trial data. A failed solution with a completed evaluation remains valid. Missing quality output is `n/a`, never zero. Failed rescoring preserves previous results, and the other trials are still rescored. Rescoring uses the current scorer image and records its ID.
- The scorer installs `media-types` for Python's system MIME mappings ([mimetypes documentation](https://docs.python.org/3.12/library/mimetypes.html)). Calibration exposed an incorrect WebP response header in the minimal image. scb-check runs ast-grep as `sg` from `PATH`, where Debian's `/usr/bin/sg` (package `login`) answered first, so its ast-grep rules were skipped without an error. The image links the ast-grep binary as `/usr/local/bin/sg` (the tool's own `sg` launcher fails). On the mvvault checkpoint 6 reference, ast-grep then flags 927 of 1850 lines and verbosity rises from 0.08 to 0.54. `scb/validate.sh` checks the MIME mapping and `sg` before the reference runs.
- Calibration: `scb/validate.sh` runs each pinned reference and an empty implementation with an empty `requirements.txt`. Every populated reference group must pass, every populated empty group must fail, and reference quality output must be present. Empty code must report the specific no-Python-files outcome (exit 2, quality null), not a numeric quality score. Some error-handling tests pass on empty code, so a zero total-pass assertion would be wrong. These checks validate this harness adapter, not skill effectiveness.

Preparation and calibration (no agent credentials or paid model calls):

```sh
bench/briefs/scb-xjq/prepare.sh /tmp/scb-xjq-baseline
SKIP_BUILD=1 bench/briefs/scb-mvvault/prepare.sh /tmp/scb-mvvault-baseline
bench/briefs/scb/validate.sh
```

Use fresh empty baseline paths. When the deferred pilot is resumed, run each brief through `bench/run-brief.sh` with the same arm set and settings. Keep all repeated rounds, including failed solutions. Infrastructure retries retain the failed artifacts and use a separately identified run. Do not change prompts, arms or tests after seeing their scores.

## Targeted tasks (`bench/briefs/skill-*`, v1.14)

Purpose: one small task per phase on which a skill of that phase should change the outcome, so each skill can run with and without itself. Skills benchmark method: inventory and usage from recorded trials (`bench/results/2026-10-16-skills-inventory.md`), these tasks, then leave-one-out ablation only for the finalist stack and only for skills with an effect here. Everything not listed here is as in the brownfield brief.

- Tasks (`brief.json` `"phase"`): `skill-plan-ttl` (plan: constraints only in the repository's docs), `skill-specify-monthly` (specify: month-end, leap-year and time-zone cases), `skill-develop-duration` (develop: a change that must reach three places), `skill-test-shipping` (test: the agent's tests against 6 hidden mutants of the source), `skill-debug-discount` (debug: a bug report that blames the wrong function), `skill-review-download` (review: a commit with path traversal and two crashes), `skill-ship-release` (ship: a release whose breaking change is only in a commit footer).
- Baseline (`prepare.sh`, no network): the fixture `repo/` as commit `chore: baseline`, then `commits/<n>/` as commits, then annotated `tags`. Fixed author and dates, checked against `baseline.sha`. Node.js 22, `node:test`, no dependencies. One step (`steps/1.md`, `"steps": "sessions"`, `"serve": "none"`), the follow-up message "Continue until the task is complete in the repository. Do not wait for approval.". One step, so the step snapshot is the final repository.
- Scoring (`checks/step1.sh` through `bench/briefs/skill-common/`): each check of `checks/checks.mjs` in its own process on its own copy of the snapshot, in `node:22.23.3-bookworm` without network, 120 s each, ids `S1-*`. The container mounts only the snapshot copy, the baseline, the runner and `checks.mjs`, and the test task's source mutants go in on stdin, so the agent's code cannot read references or mutants. A test run stopped at its time limit is no kill. Checks reach the code through its public entry points and read fixtures from the baseline. Plus `S1-regressions` (the baseline's test files, copied over the workspace's, pass) unless the task sets it aside. `checks/suite.sh`: `npm test` without install and without network. Results in `trial.json` `steps[0]`: checks, passed, suite ok, minutes, cost, follow-ups. No LLM review.
- Validation (`validate.sh` per task, `skill-common/validate-lib.sh`): the baseline fails the task's checks, the reference passes every check and its suite, each alternative valid solution (`variants/`) passes every check, and each mutant fails exactly the checks it names. Result 2026-10-16: all 7 pass (7 baselines, 7 references, 4 variants, 44 mutant cases). Each reference also passes every check and its suite with the project template of arms C and AA committed on top.
- Paired runs (not run yet): the base arm and its toggled arms (`<arm>~<skill>`, to be implemented: the base arm's image with every copy of the skill removed before the first turn, and an audit that fails the trial when the skill is still listed) in one call, k of at least 5, arm order shuffled per round, so each round has one trial with and one without each skill. The base arm's trial of a round is the "with" trial of every skill toggled in that call, so their differences share it.
- Rating per skill and task: checks passed with minus without (`steps[0].passed`), median and range over the rounds. A pair with a failed audit is dropped and counted. Next to it: in how many "with" trials the skill fired (a skill that never fired is reported as not triggered, not as no effect), minutes and API-equivalent cost added (paired median), and waited, follow-ups and `AskUserQuestion` calls with against without. No significance tests.
- Limitations: 4 to 8 checks per task, so effects are coarse. Tasks uncalibrated until the pilot (arm A, k = 1), and a task that every arm passes cannot separate skills. One task per phase, so a skill's effect holds for that task only. Arms with a project template commit its files (`AGENTS.md`, `.claude/`, `openspec/`) into the repository before the task: a release that limits the package with `.npmignore` instead of `files` fails `S1-package` on those arms only, which cancels within a pair but not across frameworks.
