Follow-up to the snapshot and restore feature, before it is released. Two gaps came up in review:

1. A snapshot can be restored into a tree of a different definition, which corrupts that tree. Each snapshot must record which definition it belongs to, and `restore()` must reject a snapshot of another definition by throwing an `Error` whose message says that the snapshot does not match the tree's definition. An MDSL definition and its equivalent JSON definition count as the same definition. Input that is not a snapshot at all (`null`, a string, a number, an array, an object without the snapshot's fields) is rejected with an `Error` too. A rejected `restore()` leaves the tree exactly as it was.
2. An action whose promise is still pending when the snapshot is taken cannot be saved. Define it this way: such an action is restored as not yet started, so the restored tree calls its action function again on its next step. Document this limitation in the README next to the snapshot API.

How we work in this repository:

- Plan the change before you edit code.
- Work test-first: write a failing test for each behavior, then the code. The tests live in `test/` like the existing ones.
- Run the repository's checks (`npm test`: lint, build with type checking, tests) and keep them passing.
- Review your own change before you finish, as a reviewer of a pull request would.
- Follow the repository's conventions: the README, its Version History table and the package version.
- Commit your work in focused commits.
