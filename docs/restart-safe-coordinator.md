# A restart-safe coordinator

This setup keeps one coordinator for a run through usage limits, account switches and restarts. A loop without a model handles routine messages, a short non-interactive cycle makes the decisions, and a watchdog relaunches only after proof that nothing else owns the run.

BenchKeeper ships this guide, not the scripts: you write, place and enable the loop, the watchdog and the timer that starts them. The reasons and sources are in the research issue [#678](https://github.com/ESchuderer/BenchKeeper/issues/678).

## Before you start

- Claude Code v2.1.259 or later, for `--permission-prompts` ([headless mode](https://code.claude.com/docs/en/headless#turn-off-permission-prompts-in-unattended-runs)).
- One profile folder per account, each signed in once interactively: `/login` is not available in `-p` ([headless mode](https://code.claude.com/docs/en/headless)). Each folder has "its own settings, session history, and claude.ai login or API key" ([authentication](https://code.claude.com/docs/en/authentication)). BenchKeeper's accounts make these folders ([setup](setup.md#accounts)).
- Usage tracking on each account: `benchkeeper accounts track <name>`. It records the reset times of the 5-hour and 7-day windows from the status line and every `rate_limit` stop ([setup](setup.md#accounts)).
- The run's folder `.benchkeeper/runs/<run id>/` in the coordinator's checkout, ignored by Git.
- GNU `timeout`. On macOS, `brew install coreutils` adds it under that name ([formula](https://github.com/Homebrew/homebrew-core/blob/main/Formula/c/coreutils.rb)).

## Set it up

1. **One owner.** Write a new random token to `<run folder>/owner` at every launch. Every cycle of the loop and the watchdog reads it first; a process whose token differs stops itself. Never stop another session without proof that it exited.
2. **Handover in two files.** `<run folder>/facts.md` is generated by the loop (not by the model) after every cycle: run id, workers with their state, open pull requests, the last status line of each worker. `<run folder>/decisions.md` is written by hand or by the cycle: the mandate in one page, decisions, caveats. A restart reads both instead of a transcript.
3. **Limit wait.** Before any launch, read `benchkeeper accounts status <name> --json` ([fields](../app/README.md#machine-readable-output)). When a window is `low`, wait until its `resetsAt`; never relaunch before it. A failure record `rate_limit` without a fresh reading means: wait for the reset of the last reading, else a fixed 30 minutes. Parse the message text ("You've hit your session limit · resets 3:45pm", [errors](https://code.claude.com/docs/en/errors)) only for an untracked account, and when the message names the session limit, ignore a parsed time more than six hours away. A weekly, Opus or Sonnet limit can reset days later (whether model limits are weekly: unverified).
4. **The loop.** Run it in the terminal the runtime binds to the run ([runtime section](#runtime-specific-orca)). It acknowledges heartbeats itself, saves every other message to `<run folder>/inbox/` before acknowledging it, removes a saved message only after a cycle for it ended without an error or a limit (otherwise the message stays for the next cycle), keeps its own heartbeat, and starts one cycle for a saved message or every 30 minutes. After two failed cycles in a row it stops its heartbeat and sends a desktop notification, so the watchdog sees the failure.
5. **The cycle.** One short non-interactive run per event, under the selected account's profile folder, with the [permission settings](#permission-settings-for-the-cycle) below. Send its JSON result to a log; a limit in the result goes to step 3. The cycle cannot ask anyone: it writes open questions to `<run folder>/questions.md`.
6. **The watchdog.** On a timer: when the loop's heartbeat is stale, wait for a limit (step 3), ping the owner once and wait ten more minutes. Relaunch with a new token only when the old loop's process has exited (its process id is gone); while it is still alive, notify instead. At most every 30 minutes and four times a night.
7. **Stop switch.** The loop and the watchdog run only while `<run folder>/active` exists. Delete it to stop both.

## Keep the coordinator a dispatcher

- Heartbeats and message checks are handled by the loop without a model. A model cycle starts only for a real message or on the timer, and reads its state from the handover files, not from a long transcript. Measured in [#724](https://github.com/ESchuderer/BenchKeeper/issues/724): a long-running orchestrator re-read about 213k tokens per model call and spent 45 percent of its shell calls on checks and heartbeats; a disposable cycle re-read about 37k.
- Picks, caps and merge rules stay deterministic, as the coordinator skill already says ([orchestrating-projects](../plugins/benchkeeper/skills/orchestrating-projects/SKILL.md#rules), the rules list); workers decide the safest reversible option instead of waiting for answers.
- Review loops follow the review rounds of the workflow skill ([full tier](../plugins/benchkeeper/skills/workflow/full-tier.md#review-rounds)): severity classes, Minor findings listed and not fixed, at most three rounds. No "until consensus" loop: voting matches debate and consensus is not correctness ([arXiv 2508.17536](https://arxiv.org/abs/2508.17536)).
- Run the cycle and simple subagent jobs on a smaller model ([costs](https://code.claude.com/docs/en/costs), [choosing a model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)). Whether outcomes hold on the smallest tier is not measured: unverified.

## Permission settings for the cycle

```sh
cd <coordinator checkout> && \
env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN -u CLAUDE_CODE_OAUTH_TOKEN -u CLAUDE_CODE_RETRY_WATCHDOG \
  CLAUDE_CONFIG_DIR=<absolute path of the profile folder> \
  timeout 15m claude -p "$(cat <supervisor folder>/cycle-prompt.md)" \
    --permission-mode dontAsk --permission-prompts none \
    --settings <supervisor folder>/cycle-settings.json \
    --max-turns 40 --output-format json
```

| Part | What it does, with the source |
|---|---|
| `--permission-mode dontAsk` | Denies every call that would otherwise prompt; reads in the working directories, the read-only command set and the allow rules still run ([headless mode](https://code.claude.com/docs/en/headless#auto-approve-tools), [permission modes](https://code.claude.com/docs/en/permission-modes)). Since v2.1.302 a `-p` run starts in Manual mode when nothing sets a mode; the flag keeps older versions from starting in another mode ([headless mode](https://code.claude.com/docs/en/headless)) |
| `--permission-prompts none` | Anything that would prompt is denied unless a `PermissionRequest` hook allows it, and the run continues ([headless mode](https://code.claude.com/docs/en/headless#turn-off-permission-prompts-in-unattended-runs)). With `dontAsk` it approves nothing by itself |
| `cd <coordinator checkout>` | The `./` path rules below resolve against the current directory ([permissions](https://code.claude.com/docs/en/permissions)) |
| `--settings <file>` | Holds the allow and deny rules. A `-p` run in a folder never trusted ignores the allow rules of the repository's `.claude/settings.json` ([permissions](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder)) |
| `CLAUDE_CONFIG_DIR` | The account's profile folder; it cannot be set from project or local settings ([authentication](https://code.claude.com/docs/en/authentication), [environment variables](https://code.claude.com/docs/en/env-vars)) |
| `env -u` of the login variables | In `-p`, `ANTHROPIC_API_KEY` is always used when present, and `CLAUDE_CODE_OAUTH_TOKEN` ranks above the stored login ([authentication](https://code.claude.com/docs/en/authentication)). `CLAUDE_CODE_RETRY_WATCHDOG` retries 429 and 529 errors indefinitely and can wait inside the run until a limit resets ([environment variables](https://code.claude.com/docs/en/env-vars)); whether a subscription session limit takes that path: unverified |
| `timeout`, `--max-turns` | Keep a cycle bounded; `--max-turns` exits with an error at the limit ([CLI reference](https://code.claude.com/docs/en/cli-reference)) |
| `--output-format json` | The result carries `is_error`, `api_error_status`, `terminal_reason` and `permission_denials` ([Agent SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript)). Which values a subscription limit produces: unverified |
| No `--bare` | Bare mode does not use the subscription login ([headless mode](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)) |

Keep the settings file and the cycle prompt outside the checkout (`<supervisor folder>`), so a cycle cannot change its own rights or its next prompt. The cycle may edit only `decisions.md` and `questions.md`; the owner token, the stop switch, the generated facts and the saved inbox are written by the loop and denied explicitly, so a later, wider allow cannot open them.

```json
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "allow": [
      "Edit(./.benchkeeper/runs/<run id>/decisions.md)", "Edit(./.benchkeeper/runs/<run id>/questions.md)",
      "Bash(gh pr view *)", "Bash(gh pr list *)", "Bash(gh pr checks *)", "Bash(gh issue view *)",
      "Bash(git status *)", "Bash(git log *)", "Bash(git diff *)"
    ],
    "deny": [
      "Edit(./.benchkeeper/runs/<run id>/owner)", "Edit(./.benchkeeper/runs/<run id>/active)",
      "Edit(./.benchkeeper/runs/<run id>/facts.md)", "Edit(./.benchkeeper/runs/<run id>/inbox/**)",
      "Bash(gh pr merge *)", "Bash(gh api *)", "Bash(git push *)",
      "Bash(git diff *--output*)", "Bash(git log *--output*)",
      "WebFetch", "WebSearch"
    ]
  }
}
```

The rules in this file come from the [permissions](https://code.claude.com/docs/en/permissions) page:

- Deny is checked before allow, and an allow rule cannot carve an exception out of a deny rule. Every part of a compound command (`&&`, `||`, `;`, `|`, `&`) must be allowed on its own.
- `git diff` and `git log` write their output to a file with `--output=<path>`, which the `Edit` rules do not see; the deny rules above close that form.
- Write path rules as `Edit(...)`: a `Write` path rule is accepted but never matches, and redirect targets (`>`, `>>`, `tee`) are checked against the `Edit` rules.
- `disableBypassPermissionsMode` works from any scope, including your own settings.
- A rule is not a security boundary around the program: a deny covers the usual invocation, not every form. The boundaries that hold are the repository's GitHub rulesets and the token's own rights.

Merges stay on the deterministic path: a script that checks `merge.*` of the policy ([orchestrating-projects](../plugins/benchkeeper/skills/orchestrating-projects/SKILL.md#recurring-runs)). The cycle has no merge right. Workers the cycle starts get no flag that bypasses or skips permission prompts.

## Test before you enable it

1. Run the watchdog in dry-run mode for each branch: limit pending, owner alive, stale owner, cap reached. It prints the decision and changes nothing.
2. With a stalled predecessor alive (its token current, its heartbeat stale), the dry run must ping and refuse to relaunch.
3. For every file a guard reads, name the step that writes it. A guard on a file nothing writes never fires.
4. Run one cycle in report mode with an empty inbox, then with one saved message.

## Runtime-specific: Orca

The commands below follow the runtime's guide (`orca skills get orchestration`) and the checks in [Orca checks](orca-checks.md).

- A restart resumes the same run: `orchestration run-use --id <run id>`. Never create a new run on restart.
- Only the terminal bound to the run consumes its inbox (observed; not stated in the runtime's guide: unverified). Start the loop in that terminal: resume the run, then start the loop.
- Drain with `orchestration check` and `--ack <delivery id>`; ack only after the message is saved.
- Liveness: only `exited` allows stop or retry; `unverifiable` is absence, not death.
- Add to the cycle's `allow`: `Bash(orca orchestration send *)`, `reply`, `worker-list`, `worker-show`, `worker-start`, `worker-release` and `task-list` in the same form.
- Add to `deny`: `check` (the loop drains the inbox; a cycle that consumes would ack messages the loop has not saved), `run-create` (a cycle never starts a new run), `worker-stop` and `worker-abandon` (stopping needs proof of exit: the cycle writes the `worker-read` evidence to `questions.md`, and you run the stop), and `Bash(orca orchestration worker-start *dangerously-skip-permissions*)` and `Bash(orca orchestration worker-start *bypassPermissions*)`.
- On Linux, outside a terminal the runtime opened, the executable is `orca-ide`: write the rules for the name the loop uses.

## Limits of this setup

- Each cycle re-reads the two handover files: keep them short.
- Not verified yet: a real night relaunch through the watchdog in loop mode, and an account switch while a cycle runs.
- Account switching stays your choice; this setup follows the selected profile and switches nothing.
