# Setup guide

What BenchKeeper installs, where it writes and how to update or undo it. The short version is the [README](../README.md).

Terms: a **tier** is how much process the `workflow` skill gives a software change (quick, standard or full). A **pack** is a named set of skills and plugins you choose per machine or project ([packs](../plugins/benchkeeper/library/README.md#packs)). The **doctor** is the app's read-only check of the machine against the setup: rules that differ, missing plugins and tools, settings that turn features off (`benchkeeper doctor`). The **ledger** is the app's record of each run, which `history` lists and `undo` reverses.

## Levels

Three levels, from the smallest: the BenchKeeper plugin ships no always-on instructions (no rule file, no hook that injects workflow context; the optional `tierBand` hook is off by default), so lite relies on the `workflow` skill description to trigger (trigger rate unverified: [evaluation](../evaluations/practices/lite-install.md)). Each level contains the one before.

Operating systems: Linux and macOS are tested. Native Windows is supported for the app and the CLI as documented here: CI runs the Windows smoke job (start, plan, apply with a ledger run). The skill install preview has no sandbox on Windows and is off unless you ask for it without one; use WSL2 for the sandboxed preview ([docs/security.md](security.md)).

Manual Windows checklist, for when a machine is available (nothing below runs in CI):

- `npx benchkeeper@6.25.0 doctor` runs and lists the installed agents.
- `plan` previews the rules, skills and settings of an installed agent and writes nothing; `apply` writes them under the user profile, and `history` undoes the run.
- `projects plan` and `projects apply` in a repository on an NTFS drive, with Git for Windows.
- The browser UI starts and "Choose folder" reports that no dialog is available, without an error.
- A WSL2 distribution runs the same commands with the sandboxed preview on.

## Setup details

The examples write `benchkeeper` for `npx benchkeeper@6.25.0`. A clone of the default branch runs a change that is not on npm yet ([app/README.md](../app/README.md#setup)).

`plan` lists each change, file changes with their diff and commands as the command line. `apply` asks per change: `--yes` applies the default selection without questions, `--all` lists the removals and asks once whether to apply all changes, including removals (`--yes --all` without the question; neither removes a plugin BenchKeeper did not install), `--pack matt-pocock` adds Matt Pocock's skills. In the browser, the Dashboard shows the doctor findings, and Fix everything walks through the global plan, the projects you pick and the steps left by hand. Each skills CLI install in a plan runs first, on a click, in a scratch folder inside an OS sandbox, so the plan lists the files it would write without a write outside that folder (Windows has no sandbox: the preview is off unless you ask for it without one; see [docs/security.md](security.md)).

What a full `apply` writes (`--level lite` or `--level standard` plans the BenchKeeper plugin alone; `benchkeeper doctor` names the level it finds and what the next one adds):

- the global rules: Claude Code `$HOME/.claude/rules/00-global.md`; Codex, Gemini CLI and Copilot a marked block in `$HOME/.codex/AGENTS.md`, `$HOME/.gemini/GEMINI.md`, `$HOME/.copilot/copilot-instructions.md` (text outside the block stays)
- the plugins BenchKeeper (its marketplace follows the `stable` branch; the app adds it once and never moves it, and the agent's own update keeps the plugin current) in Claude Code and Codex; Gemini CLI and Copilot get copies of the BenchKeeper skills in `$HOME/.gemini/skills` and `$HOME/.copilot/skills`
- Claude Code settings (merged, other keys and hooks stay): error reporting, feedback survey and `/feedback` off, local transcripts kept 14 days instead of 30, the stable update channel (typically about one week behind latest, [docs](https://code.claude.com/docs/en/setup#configure-release-channel)), subagents without a model on Sonnet, the advisor on Opus, the clear-context offer when you accept a plan, and attribution hidden: no trailer or co-author line on commits, no attribution text in pull request descriptions, no session link (`attribution` set to empty `commit` and `pr` and `sessionUrl: false`; change it in Agent settings)
- Codex commit trailer: setup writes no key for it. Current Codex reads a commit attribution switch from the account's settings (`codex-rs/ext/git-attribution/src/policy.rs` in [openai/codex](https://github.com/openai/codex/blob/main/codex-rs/ext/git-attribution/src/policy.rs)) and adds none for API-key or logged-out sessions; turn it off in the Codex account settings. The `config.toml` key named in older Codex notes is unverified for this version.
- the default model `opusplan` in Claude Code (Opus in plan mode, Sonnet otherwise), as its own change since it replaces the model you set. Orca starts `claude` without `--model`, so it applies there too. Not benchmarked.
- default effort `high` in Claude Code (also saved for Opus 5.5 and Sonnet 5.5, which ignore the global key) and in Codex, and the Claude Code auto-compact window at 400000 tokens (defaults per model: [docs](https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds)). Neither is benchmarked.
- optional, off unless chosen: the BenchKeeper status band in the Claude Code terminal and desktop app (the plugin option `tierBand` under `pluginConfigs` in `$HOME/.claude/settings.json`; plan change "BenchKeeper status band"), see [The status band](#the-status-band)
- optional, off unless chosen, only when Ponytail's band and the status band would both show (`doctor` says so): two writes that hide Ponytail's band, see [The status band](#the-status-band)
- optional, off unless chosen, only with Orca installed (its CLI answers `--version` as `orca`, as `orca-ide`, which is the name on the `PATH` on Linux outside Orca's own terminals, or as the shim `$HOME/.config/orca/linux-orca-cli-shim/orca`; the first that answers runs every Orca command): a worker-spec template for Orca orchestration and samples of `orca.yaml` and `.worktreeinclude` for new worktrees, written to the `orca` folder of the app config folder (never into a project)
- everything else installed globally, as removals that are off unless chosen: other rules files (`$HOME/.claude/CLAUDE.md`, other files in `$HOME/.claude/rules/`, `$HOME/.codex/AGENTS.override.md`), skills, plugins, marketplaces, MCP servers and hooks (Orca's own entries stay)
- the Dev Containers CLI at the newest release that is at least 7 days old (`npm i -g`, into your npm prefix), and the `find-skills` skill (with Orca: `orca-cli` and `orchestration`)

Settings files are merged: JSON by key with comments kept, Codex TOML by key, checked by parsing the result. A form the app cannot merge is reported for manual editing.

Undo: each run is recorded in `$HOME/.config/benchkeeper/ledger/`, and replaced and removed files go to `$HOME/.config/benchkeeper/backup/<run>/` (a failed backup stops its step). `benchkeeper history` lists the runs, and `benchkeeper undo <run>` (`--step` for one step, `--unit` for one installed skill, pack, plugin, rules or agent files, such as `skill:frontend-design`) restores the files and runs the recorded reverse command of each command, such as uninstalling a plugin it installed. A command without one (removing a plugin, marketplace or MCP server you had) is reported as manual: reinstall it yourself. `benchkeeper restore <name>` restores a backup folder made by the earlier `setup.sh`. The installable units (skills, packs, plugins, rules and agent files) are the ones BenchKeeper's library and catalog name: a unit of your own needs a change to BenchKeeper, and npm packages or local folders are no unit source. Diagnostics (`doctor`), setup profiles, eval cases, file checks (`verify`) and skill evals: [app/README.md](../app/README.md#commands). `benchkeeper rules check` checks rule files without a model; `/benchkeeper:reviewing-rules <file>` (Codex `$benchkeeper:reviewing-rules`) has your own agent session review one file for contradictions, vague lines, lines a tool could enforce and lines that restate the code, and changes nothing.

The app writes its setup files below your home directory and in the projects you choose, plus scratch folders in the system temp folder and the Dev Containers CLI in your npm prefix. It needs no root, sends no telemetry and never runs on its own. In a terminal it makes one request to the npm registry for a newer version and shows it (off with `BENCHKEEPER_NO_UPDATE_CHECK=1`, and when `CI` is set).

Lite level, plugin only: `npx benchkeeper@6.25.0 apply --level lite`, or by hand `claude plugin marketplace add ESchuderer/BenchKeeper#stable --sparse .claude-plugin plugins && claude plugin install benchkeeper@benchkeeper` (Codex: `codex plugin marketplace add ESchuderer/BenchKeeper@stable --sparse .claude-plugin --sparse plugins && codex plugin add benchkeeper@benchkeeper`).

## Per repo

1. Project setup, in the repository root: `npx benchkeeper@6.25.0 projects apply --agents claude,codex` (the agents the repository uses), plus `--pack <id>` for the [library packs](../plugins/benchkeeper/library/README.md#packs), `--tier` for the default tier, `--env` for where the agent runs. It writes a block (the repository rules: load the workflow skill, ask open questions in one message, fix the cause of a failed check; where commands run, default tier, skill pointers), the packs' skills from the default branch of their source, and `.benchkeeper/state.json`, whose answers later runs reuse. By default the setup stays on this machine: the block goes into `CLAUDE.local.md` (which imports `AGENTS.md`) and `AGENTS.override.md` (Codex reads it instead of `AGENTS.md`, so the app rebuilds it from `AGENTS.md` on each apply), and every file the app writes is listed in `.git/info/exclude`, so nothing lands in the repository. `--share` commits it instead: the block in `AGENTS.md` and `CLAUDE.md` with `@AGENTS.md`. Your own `AGENTS.md` text, `docs/agents/` and `.devcontainer/` stay committed either way. With `.devcontainer/` it offers `scripts/dc`, which runs one command in the dev container (`scripts/dc npm test`), and names it in the block. When dispatched Orca workers ran in the repository's worktrees, it also offers `orca.yaml` and `.worktreeinclude` at the root, off unless chosen: a new worktree gets the local setup files and runs the install command of the one lockfile at the root (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install`, `uv sync --locked`; through `scripts/dc` with a dev container), or a line to fill in. `projects plan` shows the same changes without writing. It lists the skills a pack choice adds and removes, and warns when two skills' descriptions overlap. `skills disable <name>` moves a skill to `.benchkeeper/disabled/` and `skills enable <name>` moves it back. Own packs: `benchkeeper packs save <id> --skill <name>...`, shared as one file with `packs export <id>` and `packs import <file>`; a pack file names library skills only.
2. The steps that need an agent, as a recorded session: `npx benchkeeper@6.25.0 sessions record -- claude '/benchkeeper:setting-up-projects'` (Codex: `npx benchkeeper@6.25.0 sessions record -- codex '$benchkeeper:setting-up-projects'`) for stack skills, the commands in `AGENTS.md` and the dev container. The repository must be a Git repository: the app snapshots it before and after, records the changed files (tracked and untracked, not ignored ones) and the Claude Code or Codex transcript when it finds one, and `benchkeeper undo <run>` restores those files. With the `matt-pocock` pack, also `/mattpocock-skills:setup-matt-pocock-skills` (issue tracker, triage labels, domain docs in `docs/agents/`). `doctor` warns until `docs/agents/` exists; apply the project setup again afterwards so the `## Agent skills` block it writes moves into `AGENTS.md`. In the app, the setup form and the project doctor show these lines for the project with a Copy button, and Check again reads the doctor again; the app does not run them, you paste them in your own terminal.
3. Commit the result.

Where the agent runs (`--env`):

| Env | Agent | Project commands |
|---|---|---|
| `container` (default, unless the project's own `AGENTS.md` says the agent runs on the host: then `host-agent`, or `host` without `.devcontainer/`) | inside the dev container, started with `devcontainer exec --workspace-folder . claude`; sign-in from the host environment (`CLAUDE_CODE_OAUTH_TOKEN` through `remoteEnv`) or kept in a named volume | in the container |
| `host-agent` | on the host, with Git and file edits; `--sandbox` turns on Claude Code's sandbox with `devcontainer exec` and `podman` excluded, since rootless Podman cannot start inside it ([docs](https://code.claude.com/docs/en/sandboxing)) | through `devcontainer exec`, no host fallback |
| `sandbox` | a Docker Sandboxes microVM ([docs](https://docs.docker.com/ai/sandboxes/agents/)), not tested with this setup | in the microVM |
| `host` | on the host | on the host |

Guards (`--no-guards` turns them off for the project; default on, Claude Code only): project setup adds deny rules for `--no-verify` and `-n` on `git commit` and `git push`, `git push --force` and `-f`, `sudo`, `terraform apply`, `kubectl apply` and `helm upgrade` to `permissions.deny`, and registers `.claude/hooks/benchkeeper-guard.mjs` as a `PreToolUse` hook for Bash, which denies the forms a rule cannot match (combined flags, `bash -c`, heredocs). A local setup writes them to the ignored `.claude/settings.local.json`, a shared one to `.claude/settings.json`; your own entries stay, except one identical to a rule or the hook above, which is the same entry and goes out with them when guards are turned off (`--guards` turns them on again), and undo removes only what the run added. The effect on auto mode and the sandbox is in [security](security.md#guards-in-claude-code).

Workflow load (`--no-workflow-load` turns it off for the project; default on): the project block starts with a rule line that loads the `workflow` skill before a change, issue or pull request work, or research with two or more items. That load adds the skill's text (`SKILL.md` and the guide it picks, such as `software.md`) to every such task, a typo fix included. Turned off, the line is left out of the block and the skill still loads when its description matches the task or you name it; `--workflow-load` puts the line back. The choice is kept in `.benchkeeper/state.json` as `workflowLoad: false`.

Setup scopes container mounts to the project: no host home, engine socket, privileged mode or credential forwarding beyond the sign-in variable. VS Code can forward Git credentials and SSH agents automatically ([credential sharing](https://github.com/microsoft/vscode-docs/blob/main/remote/advancedcontainers/sharing-git-credentials.md)). MCP, browser and language-server connections need container launchers; a host plugin or binary alone does not run in the container.

## Accounts

Several logins per agent, for example work and personal, each in a folder of its own. Register one with `npx benchkeeper@6.25.0 accounts add` (asks for the name and the agent; `--container --mount <path>` for a named volume in the project's dev container, mounted at that folder of the container: one its user can write, below its home folder), sign in with `accounts login <name>`, start the agent with `run --account <name> -- claude` (`codex` the same), and see the state with `accounts status` (`accounts list` shows the sign-in of each account too).

- The sign-in opens in a private browser window (Firefox, Chrome, Chromium or Edge), where no session of another account exists, so the sign-in page asks which account to use. Without such a browser, on a machine without a display or with `--no-browser`, the link is printed (Codex: with its one-time code). When the browser shows a code, paste it at the prompt.
- On the host an account is the folder `CLAUDE_CONFIG_DIR` (Claude Code) or `CODEX_HOME` (Codex) with its own login, settings and history. In a dev container it is a named volume mounted as that folder, so the sign-in survives a rebuild; the sign-in runs inside the container. A mount applies when the container is created: `accounts login` starts the container with the volumes of all container accounts and prints the command that recreates an existing one that lacks them.
- A hijacked session in a container can read the credentials in the volume or the variable ([warning](https://code.claude.com/docs/en/devcontainer)). Keep the egress firewall of that page in mind; BenchKeeper never sets `--dangerously-skip-permissions`.
- Optional token for unattended containers: `accounts login <name> --token` (Claude Code `setup-token`, a subscription is needed, requests to the model only) is kept in the OS credential store, never in a file, the registry, the ledger or `devcontainer.json`, and reaches one launch through `run --token`. Where no credential store works the command refuses. Codex: pipe the access token (`printenv NAME | benchkeeper accounts login <name> --token`) and it goes to `codex login --with-access-token` in the account's folder.
- `run`, `accounts status` and `doctor` check the sign-in first and name the command that fixes a login that is gone, and a kept token in its 11th month. Switching accounts is your choice at a launch, never inside a session, and nothing rotates accounts mid-session. Without the opt-in below, nothing switches accounts when a limit is reached either.
- Usage, Claude Code: `accounts track <name>` adds a status line script and a `StopFailure` hook to the account's folder (a plan with a diff and undo; an account that already has a status line of its own is refused, except one that only runs Ponytail's `ponytail-statusline.sh` or `.ps1`, which is replaced and comes back with `benchkeeper undo <run>` or `accounts track <name> --off`; a dev container account has no undo run, there `--off` is the way back). The status line prints what the plugin option `statusStyle` in that account's `settings.json` picks (Preferences in the app sets it per host account; a dev container account sets it with `/plugin` in a session of that account): `merged` (default) the windows and Ponytail's level from the account's `.ponytail-active` (`[PONYTAIL]`, or `[PONYTAIL:LITE]` and `[PONYTAIL:ULTRA]`, coloured as Ponytail's own badge), `plugin` the level only, `benchkeeper` the windows only, `none` nothing; the level is left out while Ponytail's `hideStatus` or `PONYTAIL_HIDE_STATUS` hides it. The windows are recorded in every style. They keep the used percentage and reset time of the 5-hour and 7-day window, and the type and time of a failed turn (one of the 12 documented error types, such as rate limit, expired login or billing error), never a credential. `accounts status`, `doctor` and the Accounts view show what is left per window (100 minus the used percentage; a reading counts only until its window resets, after that it is unknown, not full), a notice below twice the minimum and the last failure. Below the minimum headroom (defaults: 5-hour 8 percent, 7-day 3 percent, not claims about what a task needs; `accounts limits` changes them, per account too) `run` shows the account, window, what is left and the reset time, and asks before it starts; `--yes` or `accounts limits --continue-below on` starts anyway. A status line in a project's own settings takes precedence over the account's, and then no reading is kept. Between the notice level and the minimum, `run` names the account and window and starts; the choice of another account (`--account <name>`) stays yours.
- Usage, Codex: it has no feed, so `accounts status`, `doctor`, `run` and the Accounts view ask its app-server once ([`account/rateLimits/read`](https://learn.chatgpt.com/docs/app-server), run with the account's `CODEX_HOME`; a signed-in host account only) and apply the same thresholds and notices. `codex login status` reports stored credentials, not whether they still work. Auto-pick and rotation never apply to Codex accounts: the manual choice per launch and the notices stay.
- Opt-in auto-pick for Claude Code accounts, off by default (`accounts limits --auto-pick on`, and `accounts limits <name> --pool <pool>` for the accounts of one person): a new `run` under the default account that is below its minimum starts under the pool member with the most headroom, or, with no member at or above its minimum, stops with the reason or (`--when-none wait`) waits for the earliest reset. The account used is printed. It never acts inside a running session and never for an account named with `--account`. Rotating accounts at a limit may be read as bypassing a protective measure: the provider's consumer terms prohibit "bypassing any of our systems or protective measures" ([text](https://www.anthropic.com/legal/consumer-terms), section 3) and do not say either way, so the setting is yours to carry.
- Opt-in rotation by handover, Claude Code only. Default: off.
  - `accounts limits --rotate-claude handover` turns it on, `off` turns it off again. `--rotate-codex handover` is refused, and a stored Codex setting counts as off. The threshold is the account's minimum headroom, the same number that decides a launch.
  - `accounts handover <name> [--project dir]`, and `run` after the agent exits (in a terminal only), check the account. When a window is below its minimum, both windows are known, and another account of its pool is at or above its minimum, BenchKeeper shows the current account, the target account (the one with the most headroom) and the handover text, then asks. `--yes` or `--continue-below on` skips the question. Declining writes and starts nothing.
  - On yes it writes `.benchkeeper/handover.md` in the worktree and starts the agent under the target account (the `run` launcher) with that text as its first prompt.
  - What the text contains: the task and the last reported outcome, what is done (the worker's `.benchkeeper/handoff.md` fields, else the last five commit subjects), what is open, the worktree and branch, the names of uncommitted files, and the next step. It never contains transcript text, and token shapes are masked.
  - No login or credential moves between accounts, and nothing switches inside a running session. Only accounts already registered in the same pool are targets.
  - Between the notice level and the minimum, or with a window unknown or past its reset, it prints a notice and hands nothing over.
  - Terms, shown as a warning when `--rotate-claude handover` is set and before each handover: rotating accounts to extend usage may go against Anthropic's terms: the usage limits of Pro and Max assume ordinary, individual usage ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)), and the [consumer terms](https://www.anthropic.com/legal/consumer-terms) (section 3) prohibit bypassing its protective measures. The risk is the user's, and this is not legal advice.
  - Before each handover a warning also names each login variable set in the environment (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`). The agent uses such a variable instead of the account's login when it reaches the session, which happens only when `BENCHKEEPER_PASS_ENV` names it ([authentication](https://code.claude.com/docs/en/authentication)).
  - The registry keeps a folder path per account, never a token or credential, and a handover copies none.
  - Codex in dev containers: one `CODEX_HOME` volume per account and container. Never share one `auth.json` across containers that run in parallel.
- `run` gives the agent the app's filtered environment (no `GH_TOKEN`, API keys or other credentials of your shell) plus the account's one folder variable.

The Accounts view of the app does the same with fewer steps. Add Claude Code account and Add Codex account start the sign-in at once (private window, a field for the code, check) in a new folder `.local/share/benchkeeper/accounts/<agent>[-n]`, and register the account only once it is signed in. Its name comes from the address that `claude auth status` reports (field `email`, unverified: the CLI reference does not document it), with a number on a clash. `codex login status` prints no identity, so a Codex account is named `codex`, `codex-2` and so on. Advanced keeps the form with name, label, folder and dev container. Each account is a card with its sign-in, the address and plan when the status gives them, and the 5-hour and 7-day windows as bars with the percent left and the reset time. Use for new sessions makes it the default in one click, and Track usage sets up tracking for a Claude Code host account in one click. Both are runs with an undo in History. The token is set in a terminal only. Every command and its output keys: [App reference](../app/README.md#commands).

## Update

- BenchKeeper's plugin and the rules and settings: after a release ([components and changelogs](releasing.md#components)), `npx benchkeeper@<version> plan`, then `apply` (from a clone: `git -C BenchKeeper fetch --tags && git -C BenchKeeper checkout setup-v<major>.<minor>`, then the same commands through `node BenchKeeper/app/bin/benchkeeper.mjs`). The app adds BenchKeeper's marketplace at the branch `stable`, which each release moves. The plan does not update an installed plugin in the default Claude Code folder: the agent's own update does (`claude plugin marketplace update benchkeeper` and `claude plugin update benchkeeper@benchkeeper`; Codex: `codex plugin marketplace upgrade benchkeeper`). Claude Code keeps one plugin cache per config folder, so every registered host account (`benchkeeper accounts list`) has its own copy of the plugin, which the default folder's update never reaches. Third-party marketplaces such as BenchKeeper's have auto-update off by default, and `claude plugin marketplace update` refreshes only the listing, so nothing moves an installed plugin on its own ([Claude Code docs, Keep plugins updated](https://code.claude.com/docs/en/discover-plugins#keep-plugins-updated)). `benchkeeper doctor` therefore names each account whose BenchKeeper plugin is behind the app, and `benchkeeper apply` runs the marketplace refresh and `claude plugin update --scope user benchkeeper@benchkeeper` with `CLAUDE_CONFIG_DIR` set to that account's folder, only for accounts that are behind, already have the plugin and follow `stable` (an account whose folder lies outside the home folder is reported with the manual step; an account on another ref is shown in the overview and left to its own update); `benchkeeper undo <run>` puts back the account's `plugins/installed_plugins.json` and `plugins/known_marketplaces.json` (not the older version's files: Claude Code may prune them later, which leaves restored metadata that names a missing version). A running session keeps the version it loaded: start a new one. A marketplace added at another ref, for example the default branch, stays there: the app never moves or removes it, since removing a marketplace uninstalls its plugins and deletes their options and data in Claude Code. The app does not move Ponytail's marketplace or Codex's `mattpocock` marketplace: an earlier setup added them at a tag, and a marketplace keeps its stored ref, so the agent's update stays on that tag. Claude Code's Matt Pocock plugin comes from the official marketplace, which has no ref to move. To follow the default branch, remove the marketplace and add it again (`claude plugin marketplace remove ponytail`, then `claude plugin marketplace add DietrichGebert/ponytail`, then `claude plugin install ponytail@ponytail`; Codex: `codex plugin marketplace remove ponytail`, `codex plugin marketplace add DietrichGebert/ponytail`, `codex plugin add ponytail@ponytail`; Matt Pocock in Codex: `codex plugin marketplace remove mattpocock`, `codex plugin marketplace add mattpocock/skills`, `codex plugin add mattpocock-skills@mattpocock`). Removing a marketplace deletes its plugins' options and data in Claude Code, so only do this if you accept that.
- Projects: `benchkeeper projects add <dir>` (or `projects scan <root>` to find them) registers projects set up by the app. `benchkeeper projects update [dir..]` (every registered project, or only the registered ones named; in the browser: Projects, Dashboard > Fix everything, or Dashboard > one-run setup for local setups) lists each project's changes and asks once. For a local setup it writes the changes in the checkout. For a shared one (`--share`) it creates branch `chore/agent-setup-<version>` in a worktree in the app's cache folder, and commits the new setup from `.benchkeeper/state.json`. It pushes nothing: each result names the `git -C <dir> push -u origin <branch>` command, and you push and open the pull request (`--dry-run` stops after the list; the branch starts at `origin`'s default branch, or at the local one when the fetch fails). A repository that still has its setup committed (set up before 6.3) gets a commit that removes the committed copies instead (branch `chore/agent-setup-local`, also `benchkeeper projects unshare`); after you push, merge and pull it, the next Update all writes the setup locally from the answers it kept. `projects apply` refuses a local setup there until that removal is merged and pulled (`--share` keeps it committed). Shared projects with uncommitted changes and projects without a state file are skipped, and one project's failure does not stop the others. Manage the list in Projects or with `projects rename|relocate|remove`: a display name and notes (kept in the list only), Relocate for a folder that moved (the answers and the history follow), `remove` to unregister, and `remove --setup` to take BenchKeeper's setup out of a project and keep it registered (every file is listed first; a local setup is one run you can undo, a shared one a commit on the local branch `chore/remove-agent-setup` for you to push). Plugin installs and agent sessions are not part of it: run `apply` and the recorded sessions yourself.
- Matt Pocock's skills update through their marketplaces. So does Ponytail's: the app adds its marketplace without a ref and leaves an installed Ponytail, at any version or commit, to the agent's own update.
- Repository skills (library and stack) come from the default branch of their source; `skills-lock.json` records their content, the project's state file the commit installed. `benchkeeper skills list --check` and "Check for updates" on a project's Installs tab ask each source for its newest commit, `skills update` brings the outdated ones to it. A repository with many skills counts as moved when any file in it changed, so a skill can show outdated without a change of its own. `/benchkeeper:maintaining-repos` proposes bumps for pins in docs and scripts.

## The status band

Three rows of text above the prompt in the Claude Code terminal and desktop app; the VS Code extension does not draw it. It is off by default.

- Top row: the project folder, its git branch, and the level of Ponytail (a separate, optional plugin for lean code) when it is installed.
- Checks row: the last test run (`npm test`, `pnpm test`, `yarn test`, `bun test`, also with `run` and as `npm run test:<name>`, `node --test`, `playwright test`, `pytest`, `go test`, `cargo test`, `vitest` or `jest`) and the last lint or type check (`eslint`, `npm run lint`, `tsc`, `ruff`, `mypy`, `pyright`, `go vet`, `cargo clippy` or `biome`) of the main loop, each `passed`, `failed`, `not run` or `stale (N edits since)`: an edit by the main loop (Edit, Write, MultiEdit, NotebookEdit; not a subagent's, not a failed one) after a result makes it stale. A command counts when it starts the command or a part of a chain joined by `&&`, also after `npx`, `pnpm`, `pnpm exec`, `yarn`, `bunx`, `uv run` or `python -m` (`npx vitest run`, `python -m pytest`). Redirections (`> test.log`, `2>&1`, `&> test.log`) are ignored, and one `sh -c '<script>'` (also `sh -lc`, as in `devcontainer exec ... sh -lc 'cd app && npm test'`) is read as its script. A chain with `||`, `;`, `|` or `&`, a quoted name, a background run, or a failed chain that is not the check alone shows `not run`. Then the verdict for the tier (the override when set, else the tier of the last answer): `ready` when the checks the tier asks for before pushing passed after the last edit, else `checks needed:` and the missing ones. Quick asks for the tests or a lint or type check; standard and full ask for the tests and show `ready, review is yours`, as no hook sees a review. A check that failed after the last edit is always named. Research and no tier show no verdict.
- Third row: the tier of the last answer (the `Tier:` line the BenchKeeper workflow skill writes at the start of a task; `none yet` before the first), the session's override, and the buttons `quick`, `standard`, `full`, `auto`, `board`, `doctor` and `?`.

The tier buttons run `/benchkeeper:tier` (a skill of the BenchKeeper plugin) for this session (`auto` ends the override); the override survives compaction and resume. `board` opens the sessions board the app last wrote (`$HOME/.config/benchkeeper/board.html`; run `benchkeeper sessions board` or open Sessions in the app first). `doctor` asks the agent to run `benchkeeper doctor` for the project and list the findings, so the agent runs the command and the usual permission prompt applies. `?` shows a short version of this text.

Turn it on: `benchkeeper apply` and accept the change "BenchKeeper status band", the switch Terminal tier strip in the app's Preferences view, or set `tierBand` to `true` for `benchkeeper@benchkeeper` under `pluginConfigs` in `$HOME/.claude/settings.json`. Turn it off: the same switch, set that value to `false` (or `benchkeeper undo <run>` for the run that turned it on; `benchkeeper history` lists the run ids). Start a new Claude Code session after changing the option. The band reads the working folder, git, Ponytail's flag file `.ponytail-active` and the commands and edits of the main loop; it keeps the session's tier override in the plugin's own store, writes nothing else and sends nothing, and what it shows stays on this machine.

Ponytail draws a band of its own, so with both on the two stack. `benchkeeper doctor` warns (check `ponytail`) when both would show, and the plan offers to hide Ponytail's: it writes `off` to `$HOME/.claude/.ponytail-band` (what `/ponytail band off` does) and `hideStatus: true` to `$HOME/.config/ponytail/config.json`, which hides Ponytail's level in BenchKeeper's status line (Ponytail's own Claude Code status line does not read it). Ponytail's mode and skills stay active. Nothing is written until you apply that change, it is off unless chosen, and `benchkeeper undo <run>` restores both files. `/ponytail band on` shows Ponytail's band again. These are the files of Ponytail 5.3.2 (`hooks/band/register.tsx`, `hooks/ponytail-config.js` in its plugin folder); a later version may move them (unverified). Setup follows the default folders only, not `CLAUDE_CONFIG_DIR` or `XDG_CONFIG_HOME`.

## Sessions board

`benchkeeper sessions board` writes `$HOME/.config/benchkeeper/board.html` and opens it; the browser UI shows the same page under Sessions and rewrites the file on each scan, and the status band's board button opens it. Per Claude Code and Codex session on this machine: project, tier and change type (first and last tier line), the pattern (loop: `/goal`, `/loop` or a scheduled wakeup ran; group: subagents ran, their count is shown; Orca worker: a dispatched Orca worker, with the run id from the `Orca run:` line of the worker-spec template; single: none of these; when several apply, the first of Orca worker, loop, group wins), the setup installed at the time (BenchKeeper version, Matt Pocock's skills, Ponytail, packs), the skills used, the last test run, pull request links (without their state), time, tokens and, for Claude Code, the API-equivalent cost its transcript records. When Ponytail's ledger exists (`$HOME/.config/ponytail/band/*.csv`, written when its `ledger` option is on), the board also reads it, read only and offline: a session in both is one row with Ponytail's own figures (cost, turns, agent time, reuse, tests, level) in a column of their own, a ledger row without a transcript on this machine is a row marked "Ponytail ledger only", and a Source column names where each row comes from. The task name column is parsed but not kept or shown; a file that is not a Ponytail ledger, or a row that is malformed, is skipped with a note (`benchkeeper sessions board` prints it). When Ponytail's own board page exists in that folder (`board.html`), Sessions in the app shows a button that opens it in the browser; the page is not framed or copied. Pattern is detected for Claude Code sessions; for Codex only the group (subagent rollouts) is. A summary cached before the pattern was read, whose transcript is gone, shows `not recorded`. Filters by project (preset to the projects registered in the app and their Git worktrees when they have sessions, All shows every session), agent, tier, pattern, setup and period; the charts have tables beside them. It reads the transcripts in `$HOME/.claude/projects/` and `$HOME/.codex/sessions/`, and the app's run ledger, caches in `$HOME/.cache/benchkeeper/`; nothing leaves the machine.

## What the app writes and what it never does

Writes: the rules, settings and skill files of the agents you select (below your home folder), the files of a project you register (inside the folder, never its `.git` except `info/exclude`), a ledger and backups in the `.config/benchkeeper` folder of your home (created readable by you only), and, for Update all of a shared setup or one still committed, a worktree, one commit and a local branch per repository (never pushed); Update all of a local setup writes in the checkout like project setup. Commands such as plugin installs run the agents' own CLIs and write what those write; the app backs up and restores only the paths it names.

The app itself never: runs a command through a shell, writes outside the folders of a run (also through links), force pushes, deletes a remote branch, merges a pull request, runs `git clean` or `git reset` on your checkout, starts a second run while one is active, or adds telemetry. Removals are off until you select them, except removals of files the app identifies as its own by content. What leaves the machine: what `git`, `gh`, the package registries and the agents' own CLIs send (whatever an advice or eval session lets its agent read), the update notice, and the transcript of each Claude Code session while Remote Control is connected (off unless you turn it on; see [Remote Control](security.md#controls-in-claude-code)). The local server listens on 127.0.0.1 only, behind a one-time token, a cookie and a key header, and checks Host and Origin.

Which control enforces each limit, which tests cover it and which limits are still open, and what an agent does with untrusted text (web pages, issue comments, repository files) and which controls limit it: [docs/security.md](security.md). Report a vulnerability as described in [SECURITY.md](../SECURITY.md).
