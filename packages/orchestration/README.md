# @cedarloom/orchestration

The guard hook that reads every shell command a workflow's agent runs through its tools (not a skill's inline commands: Known limits), the clean environment of CedarLoom's child processes, program lookup, and the reader of Claude Code's managed settings.

## The guard hook

`@cedarloom/orchestration/guard-hook` is a Claude Code `PreToolUse` command hook for the Bash, Monitor, PowerShell and Agent tools. It takes its policy as JSON in its argument, reads the call from stdin, and refuses with exit code 2 and the reason on stderr. A workflow's agent reaches the working folder's `origin` with the policy's hub and memory repository, read for each call; `merge: "workflow"` lets an agent of any workflow script (`agent_type` `workflow-subagent` with an `agent_id`, an Agent call of that type refused there) merge a pull request of the origin's own repositories, but not of the hub or the memory repository, not with `--admin` and not by GraphQL; a branch merge without a pull request (`POST /repos/{owner}/{repo}/merges`) refuses at every level. It stops agent mistakes, not a determined hostile agent: the narrow token a session holds is the hard limit (A13).

It reads a command by structure and refuses every form outside this grammar (A79): simple commands with their assignments, redirections and wrappers (`env`, `command`, `builtin`, `exec`, `nohup`, `time`, `nice`, `timeout`, `stdbuf`, `setsid`, `ionice`, `caffeinate`, `xargs`, each with the options it knows); pipelines and lists; quotes, parameter expansions, `$(...)` and arithmetic that holds no command; heredocs and here-strings, an unquoted heredoc's `$(...)` read too; and `if`, `for`, `while` and `until`, every condition and body command read.

In the hook, all of this binds only a workflow's own agents, each with an `agent_id`: a workflow script's (`agent_type` `workflow-subagent`) and a step of the policy's package that runs as its own subagent (`<plugin>:<step>`, the policy's `plugin`). Any other caller runs untouched, merges and approvals included, as CedarLoom launches no session of its own (owner, 2026-11-09). It refuses `claude` and `codex` by name and an Agent call of a type it does not bind, one without a type (general-purpose) included. Other launchers (`npx` or `pnpm dlx` of Claude Code, `node` running its `cli.js`, a `script` or `tmux` wrapper, `orca orchestration worker-start`, other agent CLIs), a skill with `context: fork`, whose forked agent arrives as `general-purpose` with an agent id of its own and nothing that links it to the agent that ran the skill (seen with Claude Code 2.1.316), and tools outside the hook's matcher (Skill, SendMessage, MCP tools) pass, as the guard stops an agent's mistakes, not a hostile agent (coordinator decision on the forked skill, 2026-11-09).

It also refuses every caller when it cannot read the call at all: input that is no JSON, a missing or invalid policy, a crash or a timeout, the last two only where the hook's entry sets `onFailure: "block"` (Claude Code 2.1.295 or later); and a workflow's agent's call without its command or folder.

### In a session

No CedarLoom launch hands the hook to a session any more: workflows run in the agent tools, and the plugin CedarLoom builds for them ships the hook as its `PreToolUse` hook, its merges by the automation level (owner decision, 2026-11-08; [the emitter](../emitter/README.md#the-hooks)). `pnpm --filter @cedarloom/orchestration run build` bundles it, and `@cedarloom/orchestration/exit-hook`, into `packages/cli/hooks/`. How the worker launch kept a session from switching the hook off is in this file's history before that decision.

### The OS credential store

The `hub-issues` token sits in the OS credential store, and the `cedarloom work-items` commands that use it are the owner's. Nothing in them tells who asks: a session that may run them sends as the owner, so its own sandbox or permission rules have to keep it from them. CedarLoom's worker sandbox kept a worker from them until the worker launch went (2026-11-08); the trial that showed it is in this file's history.

| a function, `case`, `select`, `coproc`, `for x do` without `in`                                                                                                                   | `if` and `elif`                                                      |

| the PowerShell tool                                                                                                                                                               | the Bash tool                                                        |

### Known limits

- Data run as code when it expands: a variable's value used in arithmetic or as a subscript (`x='y[$(cmd)]'; echo $((x))`), `${x@P}`, `PS4` with `set -x`. A subscript written out with a command in it refuses, as does arithmetic in `[[ ]]` on anything but a number or a plain `$name`, and `$'...'` with a numeric escape.
- Script files and interpreters (`bash x.sh`, `npm run x`, `make`, `python3 -c`, `node -e`), and programs that run their arguments which the guard does not list (`flock`, `parallel`, `script -c`, `ssh`).
- File writes: `.git/config` and git hooks, a shell's startup files, Claude Code's settings files.
- Git configuration and hooks: sessions keep writing them, as skills and setup tools install hooks there, and the guard reads no push configuration (owner decision, 2026-11-08). A `+` refspec in `remote.<name>.push` force-pushes a push named without refspecs (`git push origin`), and `remote.<name>.mirror = true` makes a plain `git push origin` force-update `main` and push every ref. A `url.<base>.pushInsteadOf` rewrite or a `pre-push` hook (also through `core.hooksPath`) can send a push elsewhere, `main` of the memory repository included. The guard applies the rewrites the configuration holds when it reads a command to typed URLs and named remotes, but not one that the same command writes. The memory repository's `main` has no server-side rule, so nothing on GitHub refuses such a push.
- A push to the default branch, such as `git push origin HEAD:main`, passes the guard; the repository's ruleset is the limit (owner decision, 2026-11-09). So does an MCP server's merge tool, such as the GitHub MCP server's `merge_pull_request`, as the guard reads only shell calls and agents.
- A skill's or a custom command's inline command (`` !`cmd` `` or a ` ```! ` block) runs without any `PreToolUse` hook, the guard's included, once the skill's own `allowed-tools` pre-approve it. The sandbox is its only limit (owner decision, 2026-11-08: no `disableSkillShellExecution`). In a trial with Claude Code 2.1.316, a plugin skill's `` !`sh -c '…'` ``, which the guard refuses as a Bash call, ran, and a write outside the working folders failed in the sandbox. The guard as a plugin's `PreToolUse` hook does fire for the Bash calls of the agents a workflow script starts.
- A word whose value the shell knows only when it runs, such as `find . "$a"` with `a=-exec`; zsh beyond the forms above, such as `print -v` and `set -A`.
